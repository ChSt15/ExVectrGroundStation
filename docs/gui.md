# GUI: structure, views, panels, 3D view (design section 5)

Redesigned on `feature/gui-redesign` (user request 2026-11-20): views by usage instead of devices, the main groups Vehicle, Guidance and Mission left to right with the 3D view in the centre, one Operations dock for everything that is setup or diagnostics, a data-source tag and recording controls on every page, and a new dark theme with a high-contrast light option. Spec: [ground-station-design.md](ground-station-design.md) section 5. Screenshots (fake source): `docs/img/bench-1920.png`, `bench-1366.png`, `flight-1920.png`, `flight-1366.png`, `tuning-1920.png`, `tuning-1366.png`, `replay-1366.png`.

Plain ES modules in `web/`, served by the core (`GET /`, `/static/...`). No build step, no CDN, works offline (Three.js 0.170.0 is vendored in `web/vendor/three/` and resolved by the import map in `index.html`). Checked in a real headless Chromium by `tests/integration/test_gui.py` and the other `test_*_gui.py` / `*_widget.py` tests.

## Page structure

From top to bottom, identical in every view and in live and replay:

1. **Data-source tag** (`status/source_banner.js`, logic `status/source_logic.js`, unit tested in `web/test/source_logic.test.js`; user request 2026-11-20: a small pill, not a full-width banner). It leads the vehicle status row under the header, colour-coded, the tooltip gives the full text:
   - **REAL** (green) when the freshest `VehicleStatus.simulation` is false, **SIMULATION** (violet) when it is true;
   - **REAL / SIM ?** or **REAL? stale** / **SIM? stale** (amber) when no `VehicleStatus` arrived, the flag is not supplied or the packet is stale (never assumed);
   - **REPLAY** (blue), **NO CORE** (red) while the WebSocket is down.
   In the replay view a compact **replay strip** under the status bar shows the log name, the position `mm:ss / mm:ss`, playing/paused/ended, **recorded: REAL / SIMULATION / unknown** (from the replayed `VehicleStatus.simulation`), the transport (play/pause, scrubber, ±5 s, speed, keyboard space and arrows) and the small note **🔒 replay: inputs locked**. The status bar cells do not repeat the simulation flag.
2. **Header** (`header.js`): the layout views **Bench / Tuning** (Alt+1, Alt+2; remembered in `localStorage` `exgs.view`), the data view **LIVE / REPLAY**, the **command chip** (what the core's command engine reports: `CMD SENDING · POCKET`, `CMD SENDING · VIRTUAL` in amber, `CMD SENDING · IDLE`, `CMD NO LINK · ...` in red when no command link is connected, `· POCKET LOST` appended on a Pocket loss; click opens the radio tab), the **two link-direction chips** `DL` (downlink ship -> GS, from `TxModuleStats`) and `UL` (uplink GS -> ship, from `RxModuleStats`; see "Link directions"), the **recorder block** and the core connection and theme switch (dark default, light high contrast, `exgs.theme`). **Top right: yellow ABORT and red FAILSAFE** (`command/hold_ctl.js`, logic `command/button_logic.js`, `web/test/button_logic.test.js`): each is held 500 ms (fill shows progress, release cancels, no dialog), calls the core (`engine.abort`, `engine.failsafe`, see [radio.md](radio.md)) and works with the Pocket, the virtual input or none. They are disabled only with the core offline, no engine or a view-only client, and the header says why. After FAILSAFE the button reads "Clear failsafe request" (same hold) and the header blinks FAILSAFE REQUESTED (from the engine's `failsafe_latched`, never from the click).
   - Recorder block (status from `status.recorder`, logic `describeRecorder`): idle shows `not recording`, the free disk space (amber below 5 GB, red below 1 GB) and **● Record** (starts a recording at once, manual only). Recording shows a pulsing red **REC mm:ss**, the log name, its size, free space and a red **■ Stop** button (no confirmation). Recorder errors and dropped packets are shown in red. Labels, notes and the log list stay in the dock tab Recordings.
3. **Mission status bar** (`status/status_bar.js`, unchanged logic, see below). New: a red **TX POWER** line when any transmit power (LinkConfig, TxModuleStats, RxModuleStats) is above 10 dBm, so the warning is visible whichever dock tab is open (stale values stay listed and are marked).
4. **Workspace**: the view's groups (`#panels`) and the Operations dock (`#dock`) on the right.

## Views and groups

| View | Groups (left to right) | Dock | Purpose |
|---|---|---|---|
| **Bench** (default) | Vehicle: attitude, position & velocity, actuators (all compact), GNSS, health · Guidance: 3D view (full height) · Mission: mission (compact), target vs current (compact), data rates (compact) | open | everything, for bench work and setup |
| **Tuning** | Graphs: the tuning graph workspace | side rail | time-series graphs for filter and control tuning |

The **Tuning** view is described in "Tuning view" below. The old `default` and `phone` presets and the device idea are gone; a narrow window (below 1100 px) stacks the groups in one column and the page scrolls (no horizontal scroll at 390 px, tested).

**Why this arrangement.** The reading order is Vehicle → Guidance → Mission. The 3D view shows ship pose, target, trail, flaps and thrust together, which is above all the guidance picture (where the vehicle is against where it should be), so it heads the centre column and is the largest element; the numeric target-vs-current table sits right under it. Vehicle state (the inputs to guidance) is on the left, the mission (what guidance follows) on the right. Inside each group the most important values come first as big tiles with units (attitude angles, altitude and speeds, thrust and TVC; distance and errors to target; phase and mission time), then tables, then details and hints. Safety-relevant states (REAL/SIMULATION, replay, armed, motors, failsafe, failures, RC master, transmit power) are in the data-source tag, header and status bar, never only inside a panel; panels do not repeat them (the old `modes` panel is removed).

**Operations dock.** Tabs: Command first (the command buttons Mission begin, Abort, Arm / Disarm motors, Mode real / simulation, Reset, Zero estimators, driving the virtual switches under the engine's pickup rule, with the sent state, the active input and the CMD_APPLIED display; see [radio.md](radio.md)), Radio, Requests (including calibration and the home position request), Vehicle (stop altitude), Simulation testing (simulation-only wind and servo-fault requests (Force flap forces a flap's setting to an angle at once; Release all faults), hold 1 s, sent one after the other each after the vehicle's acknowledgement, greyed out unless the vehicle reports simulation mode, [requests.md](requests.md)), Link & power, Recordings, Raw sensors, Console, Inspector (`role=tablist`, arrow keys). In Bench it is a column (440 px, 380 px below 1500 px), collapsible to the rail with ⟩ (remembered per view, `exgs.dock.<view>`). In the rail (Flight) the tabs are vertical labels; a click opens the dock as an overlay over the groups (✕ or Escape closes it). The Console tab shows the number of new WARNING/ERROR vehicle lines since it was last open, and the header shows an amber calibration chip while the vehicle reports invalid calibration (both from the log watcher, [callouts.md](callouts.md)). The Failures panel (Vehicle group) also shows three calibration rows, Gyro, Accel and Mag, and a small row Ready to arm. **Primary source: the vehicle's structured `VehicleStatus.calib_state`** (decoded to `calib_gyro_ok`, `calib_accel_ok`, `calib_mag_ok`, `ready_to_arm`; used while VehicleStatus is fresh): green ok, red INVALID; the vehicle's log text only supplies the reason as the note (`last run failed`, `parameters out of range`, ...). **Fallback** when the vehicle sends no `calib_state` (older sender, value 0): the log text decides alone, as before (`LogWatcher.calibState()`), grey `—` when the vehicle has not said anything. Ready to arm is green `ready` or red `NOT ready` from `ready_to_arm`, grey `—` when unknown (no banner, no log fallback). All in `web/app/status/calib_rows.js`. A small line `Arm and MissionBegin are refused until calibrated` appears while any row is red. Display only. A tab shows a marker dot: amber while the core reports RC master, red with "Pocket also active", red/amber for a transmit power problem. **Dock panels are mounted once and survive a view change**, so switching Bench ↔ Flight does not destroy the radio widget and does not release a held RC lease (before the redesign a preset change destroyed the panel and released the lease; see the report: user decision). In replay, and without a connection, the input tabs (radio, requests, commands) show the line "replay: inputs locked: nothing can be sent from here" above the panel; the panels are now shown disabled in replay (each button disabled with its reason) instead of being hidden. Their guards are unchanged (hold to confirm, danger modal, locks, rate limits, the core's own refusal).

## Layout file

`config/layout.default.json` (served at `/config/layout.json`, path set by `[gui] layout`), validated by `web/app/layout.js` (`normalizeLayout`, unit tested):

```json
{ "default": "bench",
  "dock": { "title": "Operations", "tabs": [ { "panel": "radio", "label": "Radio" } ] },
  "views": { "bench": {
      "label": "Bench", "hint": "tooltip text",
      "columns": "minmax(250px, 1fr) minmax(320px, 1.55fr) minmax(220px, 0.85fr)",
      "dock": "open",
      "groups": [ { "id": "vehicle", "title": "Vehicle",
                    "panels": [ { "panel": "attitude", "collapsed": false, "options": { "compact": true } } ] } ] } } }
```

- `columns` is a CSS `grid-template-columns` for the groups (one column per group, in order). `dock` is `open` or `rail`.
- `options` are passed to the panel as `ctx.options`: `compact` (attitude, position, actuators, targetvs, mission, rates: fewer rows), `height` for `view3d` (`large`, `fill`).
- A panel is either a dock tab or in the groups, never both; unknown panels, duplicates and empty groups are reported in the browser console and dropped; with no valid view the fallback is one group with every panel. A remembered view that no longer exists (for example `phone`) falls back to the default.
- Collapsed state per view: `exgs.collapsed.<view>`. All storage access is wrapped in try/catch.

## Visual design

Tokens in `style.css` (`:root[data-theme=dark|light]`): surfaces, lines, text, the meaning colours (green ok, amber warn, red fault/danger, blue info, violet simulation) and the data-source tag colours; graphs will use the eight validated categorical series colours `--s1..--s8`. Type scale 11/12/13/15 px, tiles 21 px (28 px in Flight), hero 26 px (34 px in Flight); numbers in a monospace font with tabular figures. Number formats: angles 1 decimal in degrees, rates deg/s 1 decimal, positions and velocities 2 decimals (m, m/s), σ 2 decimals; units are always shown (tiles next to the value, tables in a unit column). Stale values are dimmed and struck through with their age (tiles hide the age, the panel badge shows it), missing values `—`, not supplied `n/s`.

## Behaviour

- **Connections.** The shell opens one WebSocket (mode `latest`, 20 Hz) for all panels with mode `latest`, and a second one (mode `all`) only if a mounted panel has mode `all` (the console). Subscription types are the union of the mounted panels' `consumes`; `"*"` (inspector) subscribes to everything. Only the active view is subscribed. After a reconnect the core sends a `snapshot` and the store is rebuilt.
- **View clock.** Ages are computed against the view's clock from the core (`clock` in `status` and `packets`), extrapolated with the browser's monotonic timer between messages, never the browser's wall clock. In the replay view the clock is the replay position: frozen while paused or ended, running at `speed` while playing.
- **Freshness per value (`fmt.describe`).**
  - `fresh`: normal text.
  - `stale`: older than the entry's `stale_after` (schema nominal rate if missing, else 2 s). Dimmed and struck through with an age badge. The last value stays visible.
  - `missing`: no packet of that type in this view. Shown as `—`.
  - `not supplied`: the packet arrived but the field was not in it (reduced radio set). Shown as `n/s` in italics.
  - Every value carries a small source tag (`usb`, `link`, `fake`). Values are merged field by field over all sources (user report 2026-11-22: values flickered between a number and `n/s` with the Router next to the USB): each field comes from the highest-priority source (`core.source_priority`) whose packet is fresh and carries it, else from the newest packet that carries it, with the field's own source tag and age and its own stale threshold (`web/app/store.js` `Store.get` without `src`, `describe()` in `fmt.js`). A field no connected source carries shows `not sent` (tooltip: not sent by the vehicle, with the sources checked), `n/s` with a single source; the table is in [field-sources.md](field-sources.md). Per-source access (`store.get(view, type, src)`, the inspector, the data rates panel) is unchanged. The inspector lists every (type, source).
  - Derived values (roll/pitch/yaw, tilt, vector to target, distance) use the oldest of their inputs for freshness and join the source tags.
  - Each panel header shows `stale <age>` or `no data` for the worst of its values.
- **Vehicle-reported values only.** Panels never show anything inferred from commands that were sent. Derived values are display-only arithmetic on received data and are labelled as such.

## 3D view

Panel `view3d` (the Guidance group in Bench, full height). It consumes `Attitude`, `Position` (ship pose, trail), `MissionState` (setpoint), `FlapState` and `VehicleState` (`tvc_thrust`). Everything comes from the store, so it works the same live and in replay.

**Frames** (`view3d/frames.js`, tested in `web/test/frames.test.js`):

- World: NWU (X North, Y West, Z Up). Three.js is Y-up. All vehicle content sits under one `worldRoot` group with `rotation.x = -90 deg`, which maps NWU `(x, y, z)` to Three.js `(x, z, -y)`: North is +X, West is -Z (East +Z), Up is +Y. Inside `worldRoot` positions are NWU metres and the attitude is the vehicle quaternion.
- Quaternion: the vehicle `q = [w, x, y, z]` (body to world) becomes `quaternion.set(x, y, z, w)` after normalising. A norm that deviates by more than 1 % shows "invalid attitude" (ship drawn as a ghost).
- Body frame: right-handed, +Z the long axis with the nose toward +Z, the belly faces -X (South with the identity attitude), the back +X. The flaps TL and BL are on the +Y side, TR and BR on -Y. Flap angle 0 is fully extended along +-Y, increasing angle folds the flap toward +X (the back), 90 deg is folded flat. Source: workspace `docs/system-architecture.md`, "Vehicle geometry and body frame". The ship carries a dark strip on the belly as an orientation cue.

**Scene.** Ground grid at z = 0 (1 m cells, 10 m major lines, +-50 m), axes gizmo at the origin with N, W and Up labels, a 5 m compass ring with N/W/S/E, the ship, the path (trail, see below; colour fades with age over `trail_window_s`, default 60 s), the setpoint (ghost sphere with crosshair at `MissionState.sp_pos`, a dashed line from the ship, an arrow for `sp_vel` of 1 m per m/s), and a thrust arrow along `VehicleState.tvc_thrust` (body frame) ending at the tail, scaled by `thrust_arrow.m_per_n` up to `max_m`. Optional body axes (checkbox). Target attitude (checkbox "target attitude", default on): see below. Cameras (OrbitControls): Follow (orbits the ship), Observer (orbits the origin), Top (North up, zoom only).

**Data rules.** The ship needs both attitude and position, and is not drawn without them ("no attitude and position data"). If either is stale it is drawn semi-transparent with a "stale <age>" label, never extrapolated. With no `FlapState` in the view all flaps show `default_flap_angle_deg` (45 deg) and the overlay and the actuators panel say "flap data: none (default 45 deg)". Stale flap data keeps the last angles with a "flaps stale" label. The flaps jump to the reported angle, no smoothing. The path is loaded with `get_history` on connect, on a view change and on every snapshot (so after a replay seek), then extended with live `Position` packets from the source that is currently preferred.

**Path (trail), owner request 2026-11-26** (`view3d/trail.js`, tested in `web/test/trail.test.js`). Before: the trail was time-limited (it showed only the last `trail_window_s`, 60 s, and was also capped at 4000 points; older points were pruned every refresh), so it vanished while the ship was still flying. Now:

- **Live:** the path grows without a time limit. It disappears only (a) when the operator presses **Clear path** (toolbar of the 3D view, next to the camera buttons) or (b) when a **new mission** begins. New mission is detected by one small function, `isNewMission(prev, cur)` in `view3d/trail.js`, from consecutive `MissionState` of the preferred source: `mission_mode` leaves Idle or Finished for Initialisation, Startup or Running (the rule of the "Mission beginning" callout, plus Finished), or `t_mission` jumps from >= 0 back into a countdown (< 0), or the phase goes back to Hover: the shared `restartKind` of `status/mission_clock.js`, which `isNewMission` wraps. The colour is unchanged (info colour, newest bright, fading with age over `trail_window_s` to a floor of 20 %); the old part just stays visible at the floor colour.
- **Memory:** a sample is stored only when the ship moved more than 3 cm or 100 ms passed since the last stored one (10 points/s at rest, at most 20 Hz with the radio rates). Above 300000 vertices the older half is thinned to every second point (repeatedly), the recent half and the first point stay: old segments lose resolution, nothing is dropped. At 10 points/s that is over 8 hours in full. The GL buffers grow by doubling; a path of more than 20000 points is redrawn at most four times per second.
- **Page reload (live):** the path is restored from the core's `trail` history buffer (`get_history`, Position at most 20 Hz), which keeps only the **last 600 s** (`History(window_s=600)` in `core/app.py`). A reload after a longer flight therefore restores only the last 10 minutes; the path then grows again from there. The browser does not store the path. A Clear path is not remembered over a reload (the restored path comes back). `MissionState` is now `history=True` (2 Hz, tiny; the only core change) so a mission start inside the buffer also clears the restored path.
- **Replay setting** (select in the 3D toolbar, replay view only, remembered in the browser as `exgs.trail` in localStorage): **Path up to now** (default): the path from the start of the recording, or of the current mission (the last new mission at or before the replay position), up to the replay position. Playing extends it, a seek recomputes it from the log history, seeking back shortens it, seeking over a mission start restarts it. **Entire path**: the whole recorded path (Position of the whole log, at most 20 Hz) at once, regardless of the replay position, with a yellow marker at the current position; points after the replay position are drawn at the floor colour, Clear path is disabled. Scrubbing refetches the entire path only after 400 ms of quiet. Clear path in replay lasts until the next seek or view change.
- Display only: nothing is sent to the vehicle, no mission or safety decision is made here.

**Model config** (`config/model.<name>.json`, set by `[gui] model`, served at `/config/model.json`, files in `models/` at `/models/`). The placeholder is a procedural ship with the owner's real dimensions (2026-11-21, all named in `dimensions_m` of the config, metres, measured from the bottom of the ship): tube 13 cm diameter and 54 cm high, parabolic nose 20 cm high on top of the tube (total 74 cm), origin on the axis at the centre of mass in the middle of the ship (37 cm from the bottom, so the tube ends at z = +0.17 and the nose tip is at z = +0.37). Top flaps 7 x 14 cm with the lower edge 53 cm from the bottom (pivot z = +0.23), bottom flaps 8 x 21 cm with the lower edge 1 cm from the bottom (they span 0.01 to 0.22 m above the bottom, pivot = flap centre at 0.115 m, z = -0.255), 8 cm chamfer on the top (nose side) of every flap. Extended flaps (angle 0) lie in the Y-Z plane through the axis, not swept, hinge parallel to the axis on the tube surface at y = +-6.5 cm. The top flaps start 1 cm below the tube end, so most of their length sits beside the nose. The top flaps are tilted inward by `dimensions_m.top_flap_cant_deg` (10 deg, per-flap `cant_deg`, positive = upper end toward the axis) about their lower hinge point (pivot minus half the flap length, so the lower point stays on the tube and the upper end moves toward the axis by about length x sin(cant), 2.4 cm for the top flaps). The deflection angle (0 = extended, increasing = folded toward the back) applies on top of the cant, about the tilted hinge. The flight simulator uses the same names and values.

```json
{ "name": "placeholder",
  "body": { "source": { "primitive": "starship-placeholder", "height_m": 0.74, "radius_m": 0.065,
                        "nose_length_m": 0.20, "origin_from_bottom_m": 0.37 },
            "model_to_body": { "rotation_deg_xyz": [0, 0, 0], "translation_m": [0, 0, 0], "scale": 1.0 } },
  "flaps": [ { "id": "tl", "index": 0,
               "source": { "primitive": "flap", "width_m": 0.07, "height_m": 0.14, "thickness_m": 0.004,
                           "chamfer_m": 0.08, "chamfer_corner": "out_top" },
               "model_to_body": { "rotation_deg_xyz": [0, 0, 90], "translation_m": [0, 0.065, 0.23] },
               "pivot_body_m": [0, 0.065, 0.23], "axis_body": [0, 0, 1], "sign": -1, "model_angle_deg": 0 } ],
  "default_flap_angle_deg": 45,
  "thrust_arrow": { "m_per_n": 0.02, "max_m": 0.6, "origin_body_m": [0, 0, -0.37] },
  "trail_window_s": 60 }
```

- `source`: `{ "primitive": name, ...parameters }` (`starship-placeholder`, `flap`) or `{ "gltf": "models/ship.glb", "node": null }`. With `node` set, that node of the file is used (its own transform in the file is ignored) so the body and the flaps can be nodes of one file or separate files. Both go through the same loader and the same transforms.
- `model_to_body` (body and, as an extension of the design, each flap): rotation as Euler XYZ in degrees, translation in metres, uniform scale, mapping the model's own frame into the body frame **at the modelled angle**. glTF is Y-up, so a glTF ship with its long axis along Y needs `[90, 0, 0]` (glTF Y goes to body Z, glTF Z to body -Y). The primitives are built directly in the body frame.
- Flaps: `pivot_body_m` and `axis_body` (body frame, unit vector) define the hinge. The pivot group rotates by `sign * (angle - model_angle_deg)` about the axis, `angle` in the vehicle convention and `model_angle_deg` the angle at which the flap is modelled in its file. `index` selects the element of `FlapState.angle` (0 tl, 1 tr, 2 bl, 3 br).
- Placeholder flap plate: hinge on the model's Z axis, the plate extends toward +X, `chamfer_m` is the length of a 45 deg cut at the outer corner named by the orientation parameter `chamfer_corner`: `out_top` (toward the nose, +Z) or `out_bottom` (toward the tail). **All four flaps use `out_top`** (user decision 2026-11-20: the bottom flaps were drawn upside down with the chamfer at the bottom); a flap that is modelled the other way up is fixed by this one parameter in its config entry, never by rotating it. The architecture note gives only "8 cm chamfer"; the 45 deg cut is an assumption of the placeholder and, like the corner, changes by config only. The pivot is at the flap's vertical centre on the body surface at +-Y (z = +0.23 m top, -0.255 m bottom; the top flaps span z = +0.16 to +0.30 m, the bottom flaps z = -0.36 to -0.15 m, before the cant of the top flaps).

**Swapping in a real glTF model** (config change only, no code):

1. Put the file in `models/` (for example `models/starship.glb`) and copy `config/model.placeholder.json` to `config/model.starship.json`.
2. Body: `"source": { "gltf": "models/starship.glb", "node": "hull" }` and `model_to_body` so that the model's nose points to body +Z, the belly to -X and the origin sits at the centre of mass (glTF Y-up long axis: `rotation_deg_xyz: [90, 0, 0]` plus a translation if the file's origin is elsewhere).
3. Flaps: either `{ "gltf": ..., "node": "flap_tl" }` per flap or separate files. Set `pivot_body_m` to the hinge in the body frame, `axis_body` and `sign` so that increasing angle folds toward +X, and `model_angle_deg` to the angle the flap has in the file (0 if modelled extended). Check with the checkbox "body axes" and by watching the flaps move.
4. Set `[gui] model = "config/model.starship.json"` in the core config and reload the page. A config that fails validation, or a model that fails to load, shows "3D view unavailable: ..." in the panel, and the rest of the GUI keeps working. Run `.venv/bin/pytest tests/integration/test_view3d.py` to re-check the loader with `models/test-box.gltf`.

**Ground distance.** The downward lidar reading `Position.ground_distance` (m, 2 decimals; moved from Actuators 2026-11-26, schema 0x93EF9C5F) is the fourth tile of the Position & velocity panel (`status/ground_distance.js`: grey `no reading` when NaN, i.e. real sensor out of range or stale, the vehicle reports a valid reading only in 0.4 to 1.5 m; dimmed when the Position packet is older than 3 s). It is the vehicle's estimate of the distance to the ground, valid only in the sensor's useful range. It is a Tuning graph signal (`Ground distance`, `pos.ground_distance`, so also exportable; saved graph configs with the old id `act.ground_distance` are mapped to it on load), it feeds the Systems/health text, and it is recorded with every `Position` packet (the recorder stores all schema fields) and shown in replay like the live value. Old recordings (ground distance in `Actuators`) load without errors and show `no reading`.

**Target attitude (display only).** The vehicle's attitude setpoint `MissionState.sp_q` (quaternion body to world, NWU, from `MISSION` / `AIR_MISSION`) is drawn as three thin dashed, semi-transparent "ghost" body axes (X red, Y green, Z blue, the colours of the real body axes) at the ship position, with the same conversion as the ship (`vehicleQuatToThree`, `view3d/frames.js`), so they coincide with the real axes when the vehicle tracks perfectly. They are hidden when `sp_q` is None (all four zero, NaN from an older sender, or a link without it), stale or unusable, and with the checkbox off. The overlay reads "attitude error (setpoint vs estimate): N.N°", the shortest-arc angle between `Attitude.q` and `sp_q`. No smoothing, nothing sent to the vehicle. Note: the vehicle's flap controllers only control the direction of body +Z, so during bellyflop and freefall the published setpoint roll follows the real roll: the error then shows only the pointing error, not roll.

**Target smoothing (display only).** The target sphere shown in the 3D view is smoothed: it is **not** the raw reported `sp_pos`. It is a critically damped second-order follower (time constant 0.25 s) of the reported `sp_pos` with feed-forward velocity (`view3d/target_smooth.js`, tested in `web/test/target_smooth.test.js`). Between packets the follower's goal is extrapolated with the target velocity, but never beyond one packet interval plus 50 ms (1.25 x the measured interval + 0.05 s, at most 0.5 s), then it holds. The velocity is `sp_vel` when it agrees with the difference of consecutive `sp_pos` values, else that difference, because `sp_vel` is not the derivative of `sp_pos` in every phase (in the recorded run it is 0 while `sp_pos` moves 5 m/s in Deceleration and 0.2 m/s in Landing). A jump between two packets implying more than 30 m/s is a guidance step (phase change, waypoint): the display glides to the new position within about a second instead of teleporting, and no velocity is derived from it. A continuous motion is followed without lag. The follower runs on the view clock (packet arrival, the packets carry no own timestamp), resets on replay seeks, view changes and stale MissionState. Panels and plots keep the raw vehicle-reported `sp_pos` and `sp_vel`; nothing is sent to the vehicle. Evidence and numbers: `tools/analyse_target_smoothing.py` on a recorded run (USB 20 Hz and a simulated 5 Hz radio path with 1 mm / 0.01 m/s quantisation and jitter): visible stutter (change of the per-frame displacement) at 5 Hz p99 / max 5.2 / 98 mm with the previous extrapolation + 150 ms blend versus 2.0 / 14 mm now, and the per-frame jump at a guidance step 7.3 m versus 0.47 m.

**Debug hook** for end-to-end tests: `window.exgs.view3d.debug()` returns the ship pose and visibility, nose, belly and origin in Three.js coordinates, per-flap angle and outer-edge position in the body frame, flap source (`data`, `default`, `stale`), setpoint and thrust visibility, trail point count, overlay text and camera mode. `window.exgs.view3d.scene3d` gives the Scene3D object.

## GNSS panel and altitude cross-check

Panel `gnss` (`panels/gnss.js`, logic in `gnss/gnss_logic.js`, unit tested in `web/test/gnss_logic.test.js`). Vehicle-reported values only; the cross-check compares two reported values and **sends nothing**: it never changes anything on the vehicle and is never the only warning. Data: the `Gps` packet, which is the USB `GNSS` (0x83, all fields) or the radio's `AIR_GNSS` (10 Hz position and velocity) merged by the wire profile with the 1 Hz `AIR_GNSS_INFO` (`docs/wire-profiles.md`).

- **Content (compact, no scrolling).** Latitude / longitude in degrees (7 digits) on one row, absolute GNSS altitude (the receiver's altitude: u-blox height above the WGS-84 ellipsoid, not above sea level), the velocity in NWU (N, W, U m/s; the decoded `Gps.vel` is already NWU, shown unconverted; moving east reads negative W, descending negative U), tiles for satellites, fix type name and the altitude cross-check status, and tiles for the receiver's own accuracy estimates (1 sigma): horizontal, vertical and speed (`vel_acc`, USB GNSS only, "—" otherwise). Without a fix (`None` values) the panel shows "—" and "no fix", never stale numbers as current. Removed from the panel on owner request (2026-11-22): the relative altitude and ground speed tiles, the NWU rows, the fix-quality section and the age of the info; the relative altitude and the other values remain available as graph signals.
- **Altitude cross-check.** Its status is the "Alt check" tile (ok / difference X m, warning / MISMATCH / no data / no fix / no reference); the optional `Altitude mismatch` callout and graph signals use the same logic. The reference is the `HOME_POSITION` altitude (when `ALT_VALID` and its `epoch` equals `VehicleStatus.home_epoch`), else the mean of the first valid GNSS altitudes taken on the pad; settings `altcheck.limit_m`, `altcheck.hold_s`, `altcheck.hysteresis_m`, see `docs/callouts.md`.
- **Home and position relative to home (owner request 2026-11-26, `feature/home-display`; reverses the removal of 2026-11-22).** A "Home" row under the absolute altitude shows the `HOME_POSITION` exactly as the vehicle reported it (latitude / longitude in degrees, altitude, `(simulation)` flag, `epoch`; "no home position received yet" before one arrives; it is a fixed reference and is never greyed as stale). The first row of the N / W / U table, "Position vs home", is the GNSS position in metres relative to home in NWU, **derived in the ground station** (`gnssNwuFromHome` in `gnss/gnss_logic.js`, pure, display only): local tangent plane at the home latitude on the WGS-84 ellipsoid, N = dlat * M, W = -dlon * N' * cos(lat0) (east is negative W), U = GNSS altitude - home altitude (same datum). It shows "n/s" while there is no home or no usable fix (fix type below 3-D when known); with a home without a valid altitude N and W show and U is "—". Nothing is derived without a home, and nothing is sent. The home is requested automatically at T-5 (`[requests] auto_home`, [requests.md](requests.md)) or by hand in the Requests panel. In REPLAY the same panel recomputes the metres from the logged `HomePosition` and `Gps` at the replay time (the recorder keeps every packet, so nothing extra is logged; the metres themselves are not stored).
- **Graphs.** Signals `gnss.alt` (absolute), `gnss.alt_rel` (relative to the home altitude or the start, as above, computed per sample from the latest `HomePosition` / `Position`) and `gnss.alt_diff` (estimated minus GNSS), preset graph "Altitude cross-check" (estimated, GNSS relative, difference). Derived signals of the same panel (group "GNSS position", metres): `gnss.home.N`, `gnss.home.W`, `gnss.home.U` (the NWU position relative to the latest `HomePosition`, per `Gps` sample) and `gnss.home.h` (horizontal distance from home); preset graph "GNSS position relative to home vs estimate" (GNSS N / W solid, `Position` N / W dashed). They need a home: the Tuning view takes the home from the view's state store when it loads its history (`HomePosition` is not in the plot history; a home received later is added live), and in replay the home at the replay time is used for the whole window. `Gps.lat` / `lon` are in the plot history fields now. `Gps` is in the plot history now (10 Hz).
- **Audio.** Optional callout `Altitude mismatch` (callouts category `altcheck`, off by default) once per excursion. No recorded clip exists yet (piper was not available): it uses the browser voice or beeps until `altitude-mismatch` is added to `web/audio/phrases.json` and the clips are regenerated.

Since the GS-control cutover the core's command engine is the only sender of vehicle commands and runs without any client ([radio.md](radio.md)); the widget only feeds the engine the virtual switches while this client holds the panel lease and the Pocket is not live (the real Pocket wins). Rules, enforced in `radio_logic.js` / `radio_widget.js` and covered by the tests:

- **Always the core's state.** Every control, the µs readout and the banner come from the `rc` push messages (the panel's state; what the vehicle applied is in the Command tab). A click sends a request (`rc.set`) and changes nothing locally; the control moves when the core reports it. The one exception is the slider thumb while it is being dragged.
- **Config driven.** The controls, their kinds, positions on the handset (`svg = {x, y}`), labels and `meaning` tooltips come from `config.get radio`. SD is labelled "motors armed / disarmed".
- **Banners** (from `rc.mode`, `rc.command`, `holder_is_you`, connection and view): a chip `VIRTUAL` (amber) / `POCKET` (blue) / `IDLE`, and the banner: `VIRTUAL · input of the command engine · command stream 25 Hz to <links>`, `POCKET live · input of the command engine · ...`, `NO INPUT · the core holds its last command state`, `NO COMMAND LINK CONNECTED` when the engine has no connected command link, `VIRTUAL (<holder>)` for another client's lease, red `DISCONNECTED · the core keeps sending its command state without the GUI`, violet `REPLAY`. A red **warning** banner: `WARNING: Pocket stream lost. The ground station keeps sending its last command state (SE released); after the Pocket returns, a switch in an unsafe position must be cycled first` while the engine reports the Pocket lost (a toast is raised from the core's event as well; no abort and no failsafe is sent), and `The Pocket is the input: the virtual switches are inactive while it is live` while the panel is held but the Pocket is live. An amber **pickup hint** box lists what the input waits for: `SA is up while go is off: flip it down first`, the same for SD (motors disarmed) and SE, and `SC: flip to REAL (position 0)` / `SIMULATION (position 1 or 2)` to take over. The buttons are "Use virtual switches" (`rc.acquire`) and, for the holder, "Release virtual switches".
- **Operable only while this client holds the lease, the core reports `virtual` and the Pocket is not live.** Otherwise all controls are read-only (idle, Pocket live, someone else holds the panel, disconnected, replay). "Use virtual switches" is enabled only when the core said this client may control (`welcome.can_control`), the view is live and nobody holds the lease; it is **also available while the Pocket is live** (it then has no effect until the Pocket stops). A new holder starts at what the engine is sending (the panel is preset to the output: SD shows armed with its guard open if the motors are armed), so taking the panel changes nothing that is sent.
- **Heartbeat** `rc.heartbeat` every 300 ms while this client holds the lease. Closing the tab or losing the connection ends the lease at once (WebSocket close), a stalled page within 1 s: the panel returns to its defaults and the **engine keeps sending its last command state** (it needs no client). After a reconnect the client does **not** take the panel again by itself.
- **Controls.** `toggle2`: click flips. `switch3`: click the top, middle or bottom zone, or arrow keys / space (SC: position 0 = REAL, 1 and 2 = SIMULATION). `momentary` (SE): `SE=1` on pointerdown and every 100 ms while held, `SE=0` on pointerup, pointercancel, lost pointer capture, window blur and when the page is hidden (the core also releases it 300 ms after the last refresh; the engine stretches a press to at least 160 ms). `slider` (S1): display only.
- **Padlock.** A control with `lock` in the radio config (SD, motors armed) is shown as a padlock while the core reports it locked: hold it for 1 s (progress bar) to send `rc.unlock`. The guard has no timeout: while unlocked the switch is operable and the label reads `unlocked · disarmed` or `unlocked · armed` (no countdown), with a **Lock** button (`rc.lock`, back to disarmed, guard closed). Disarming is always immediate. A reset event (core start, SE system reset, GS failsafe request, lease end) closes the guard on the next push. The Command panel's Arm (hold 1 s: `rc.unlock` then `rc.set SD 1`) leaves the guard open; its Disarm button sets SD to 0 directly.
- **Replay.** In the replay view the widget shows the recorded `RcState` read-only under the REPLAY banner. Switching to replay while this client holds the panel asks "Release control and switch to replay?" (in-page dialog); the release is sent before the view changes.
- **Sticks (display only).** Under the handset two gimbal boxes show the stick channels: the Pocket's sticks as received when it is live (stale after 0.5 s, greyed), otherwise the channel defaults; the ground station sends no stick values. The channel assignment comes from the radio config's `[sticks]` table.
- **Dock tab marker** (the tab's alert state): amber while a Pocket loss is reported, red while the vehicle reports NOT MASTER or MULTI_MASTER.
- **Debug hook** `window.exgs.radio.debug()`: banner text and tone, button states, and per control the displayed position, enabled, lock state, padlock visibility and the µs text.

## Display settings (UI scale and 3D resolution)

The panel shows the rate of each type of data with the path it took, from the core's `get_rates` (docs/api.md), polled once per second for the current data view (`ctx.rates()`).

- **Table** (sorted by path, then bytes/s): type, path, source (with the origin node), Hz over 2 s, Hz over 10 s, nominal Hz, bytes/s, age. Paths: **air** (frames from node 1 or 3 received through the Router), **usb direct** (the vehicle on its own USB), **router local** (made by the Router, node 2, and the Pocket's RC_STATE copy: never on the air), `simulated` (fake source, or a recording) and `unknown`. A **total row** closes each path. Nominal is the schema's `rate_air` on the air path and `rate_usb` elsewhere (a dash when the schema has none; for the fake source and replay the type's nominal rate). **Greyed**: not seen for 3 s (or three nominal periods), or a zero rate. **Orange**: below 70 % of the nominal rate (judged on the 10 s window below 2 Hz, so a 0.5 Hz stream does not flicker).
- **Bytes/s** are wire bytes as received on the serial line (COBS, delimiter, stream kind, CRC and network header included) when the profile reports the frame size (`exvectrnet-1` does); the air total and the bar use **payload** bytes. Packet-level streams (fake source, replay) have no byte counts and show `n/a`.
- **Air utilisation bars, one per direction** (the air link is time-division with a 1:1 split: 25 air packets/s of 253 payload bytes each way, about 6.1 kB/s of payload in each direction at the same time; the total is not shared): **Downlink** (ship radio node to Router to ground station, vehicle telemetry; measured: payload B/s of frames from node 1 or 3 received through the Router) against `[rates] air_capacity_down_bytes_s`, and **Uplink**, an **ESTIMATE** (labelled "estimated" on the bar and its tooltip) because the ground station cannot see uplink bytes: the GS `CMD_STATE` at the uplink rate of 25 Hz (14 B; the Pocket's `RC_STATE` no longer goes to the air) while the engine sends, `LINK_CONFIG` at its schema rate, plus the `REQUEST`s and telecommands this ground station sent through a Router, against `[rates] air_capacity_up_bytes_s` (both default 6100; `air_capacity_bytes_s` is a compatibility alias). Next to each bar the measured air packets per second against the 25 packets/s maximum, from the `air_rx_ok` counters of the Router (down) and the ship radio node (up); the downlink is limited by packets as well as bytes (each air packet carries at most 253 payload bytes and each packet type at most once). Amber above 80 %, red above 100 %. A measured uplink byte count would need a per-direction byte counter in the firmware's `LINK_STATS` (a possible later schema addition; not done). Below the bars the Router's own LINK_STATS (`RadioLinkStats`: air packets per second up and down) and the link quality of both directions, labelled "Downlink (ship -> GS)" and "Uplink (GS -> ship)" ("no data" when a direction was never received). Details: docs/api.md `get_rates`.
- **Status bar**: the per-source chips are labelled "frames/s on the serial hop:" (tooltip: it is the ground station to Pocket/USB hop, not the radio rate) and an **air: X B/s** chip (payload bytes of the air path; `air: n/a` when not measured) follows them.
- **Replay**: the numbers are computed from the recording in replay time (the packets' own timestamps against the replay position, so pause, seek and speed behave), packet level only: no byte counts, so no air bytes (`air: n/a`); one wire frame can give several packet types, so Hz is per packet type. Paths come from the log's `#source` kind and the type (a log has no node ids).

- **Frames, not samples**: the table counts wire frames per packet type. An `AIR_ACTUATORS` frame (nominal 25 Hz, path air) carries **two** actuator samples, so the `Actuators` and `FlapState` panels, plots and recordings see an effective 50 Hz (the history keeps at most 20 Hz per series as for every type). `AIR_MISSION` is nominal 5 Hz. Nominal rates come from the schema (`rate_air`, `rate_usb`).

Tests: `web/test/rates_logic.test.js`, `tests/integration/test_rates_gui.py` (pty fake vehicles: table content and path labels; replay).

### Link directions (link panel, header chips, rates panel, plots; `link/lq_logic.js`, `web/test/lq_logic.test.js`)

| Direction | Packet | Measured by | Meaning of `rx_lq`, `rssi`, `snr` |
|---|---|---|---|
| **Downlink (ship -> GS)** | `TxModuleStats` | the Router (node 2, the TX module in the Pocket) | what the Router receives from the ship |
| **Uplink (GS -> ship)** | `RxModuleStats` | the ship radio node (node 3), forwarded by the Router | what the ship receives from the ground station |

- **Data rates panel**: one link-quality row per direction.
- **Tuning catalogue** (group "Link quality"): `link.dl.lq|rssi|snr` (Downlink, `TxModuleStats`) and `link.ul.lq|rssi|snr` (Uplink, `RxModuleStats`), and the presets "Link quality up/down (LQ)", "Link RSSI up/down", "Link SNR up/down". - Both packets are recorded like every packet and shown in replay. No callout or health rule warns on link quality (the only link callouts are `Router link lost` / `Telemetry lost`, which are about sources, not a direction); any future one must name its direction.
- The fake source's radio profile sends both (downlink 92 %, uplink 96 %).
- **Node log lines**: the ship and radio nodes may print `AIRDIAG key=value ...` lines (ExVectrLink instrumentation). They arrive as `LOG_TEXT` (up to 233 bytes) and are shown whole in the Console panel (no truncation, wrapped); there is no AIRDIAG panel yet.

### Raw and calibrated sensor panel

`web/app/panels/rawsensors.js`, `web/app/sensors/rawsensors_logic.js` (`web/test/rawsensors_logic.test.js`). Panel `rawsensors`, "Raw and calibrated sensors". Consumes `ImuRaw` and `Calibration` (the vehicle's `CALIBRATION` packet, port 0x93, USB only, every 2 s). Needs the vehicle's USB debug set: with no connected `vehicle_usb` source in the live view the panel says so.

- **Raw (uncalibrated):** `ImuRaw` gyro (rad/s), accelerometer (m/s²), magnetometer (shown in µT, the packet is in T), pressure (Pa) and temperature (K), live, with the update age (stale values are struck through with their age, as everywhere), the magnitude of accel and mag, and a sparkline of the last 10 s (magnitude for vectors). The column header says **raw (uncalibrated)**.
- **Calibrated (computed here with the ship's formulas):** the formulas of flight-software `docs/project/hardware-and-drivers.md` section 8a, computed in the browser from the latest `ImuRaw` and `Calibration`, SI units: `gyro_cal = gyro_matrix * (gyro - gyro_offset)`, `accel_cal = accel_matrix * (accel - accel_offset)`, `mag_cal = mag_matrix * (mag - mag_offset)`, `omega_est = gyro_cal - gyro_bias_est`; matrices are row-major, `M[r][c] = matrix[3r + c]`. Calibrated values and magnitudes (|accel cal| should be about 9.81 m/s² when the vehicle is still) are shown next to the raw ones; the magnetometer in µT (the vehicle normalises |mag cal| to about 5 µT, which is not the physical field strength). A component that is NaN on the wire gives "n/a", never a guessed number; a `raw_frame` other than 0 (SENSOR) is not computed. **Display only:** nothing computed here is sent, stored, used for a decision or fed back anywhere.
- **Calibration state:** a line shows the age of the `CALIBRATION` packet (marked STALE when it is older than its limit, and the calibrated column is then dimmed) and the source flags per sensor, decoded: calib EEPROM, transform EEPROM, offset override (hard-coded), RAM only (not saved), memory cleared (defaults), or identity defaults when no bit is set. Until a `CALIBRATION` packet has been received the calibrated column shows `waiting for CALIBRATION packet` (and the state line `none received`).
- **Tests:** the formula is checked against the `imu_raw` and `calibration` cases of the Packets test vectors (`web/test/data/calibration_vectors.json` is a copy, a Python test fails when it drifts from `lib/ExVectrPackets/test/vectors/packets.json`).

`Estimator.att_std` changed meaning on the vehicle (packet version 2 here): it is the 1 sigma of small rotations about the **WORLD axes [North, West, Up]**, no longer a per-quaternion-axis value. The packet labels are `north, west, up` and the inspector shows them that way.

In replay see "Replay" below.
- **Mission time source (2026-11-26).** PRIMARY: the vehicle's own `MissionState.mission_elapsed` (`MISSION` 0x82 and `AIR_MISSION` 0x23, schema `0xF49ACD01`; seconds since the mission's T0, negative in the countdown, continuous across all steps, held at the final value after the chain ends, `None` when no mission has begun or after a reset to Idle). A new mission is exactly when it resets: it jumps back by more than 1 s, or goes from NaN / the held final value to a negative value; no phase or mode inference. The final value held for more than 1 s ends the mission (`endReason` `held`, the time then stays frozen); NaN ends it as `reset`. Between samples (2 to 5 Hz) the value is linearly interpolated from the recorded samples (graph axis, events panel, replay: at the replay position), extrapolated at most 1 s beyond the newest sample of a running mission. The Mission panel tile shows the SMOOTH live counter (`status/mission_smooth.js`, tests `web/test/mission_smooth.test.js`): anchored to the telemetry and the local monotonic clock, 1 s/s between samples, an error absorbed over 0.5 s, never backwards, snap on a reset / an error above 1 s / when the clock stops or starts, no extrapolation beyond 2 s without a sample; in replay the tile follows the replay position from the recorded samples. FALLBACK: when no sample carries the field (old recordings, old senders) the DERIVED clock below applies; the tile's tooltip says `derived`. `MissionClock.source` is `telemetry` or `derived`; `timeIn(m, t)` / `sampleIn(m, tm)` map within one mission (telemetry: interpolated, derived: t - T0). The `get_history` plot fields and `get_events` samples carry `mission_elapsed` and `mission_mode`.
- **x axis (mission time).** Tick labels, the cursor readout and the axis title show the time since the start of the whole MISSION: `T-30`, `T0`, `T+12.5` ("mission time (s)"). `MissionState.t_mission` restarts with every step of the mission chain, so it is not used directly: the shared pure module `web/app/status/mission_clock.js` (tests `web/test/mission_clock.test.js`) builds one continuous clock from the `MissionState` samples (`t_mission`, `mission_phase`) of the plot history, live and replay, recomputed from the history (so a seek gives the same result, no running accumulator). A mission starts with a countdown (`t_mission` < 0) when none is running, or when ANY new-mission rule fires (list below), also while the previous mission is still running (it then ends with reason `restarted`); T0 is the sample time at which `t_mission` reaches 0 (projected from the latest sample while the countdown runs); after T0 the mission time is sample time minus T0 across ALL steps (a step restart of `t_mission` to a value >= 0 does not reset it). **New-mission rules** (one pure function `restartKind(prev, cur)` in `mission_clock.js`, used by the clock in live, reload and replay alike and by the 3D trail's `isNewMission`): (1) `mission_mode` goes from Idle or Finished to Initialisation, Startup or Running; (2) `t_mission` jumps from >= 0 back to < 0 (a countdown again; counted only when the running mission had passed T0, so a negative step clock before T0 is not a restart, but one after T0 is); (3) `mission_phase` goes from a later phase (Ascent .. Landing) or Completed back to Hover. A start from rule 1 or 3 takes T0 only from a following sample (the first `t_mission` may still be the old mission's). `VehicleStatus.home_epoch` and `mission_index` are not used (not in the MissionState feed, or per-step). A mission ends at phase Completed, at a fall back to Idle from a running phase, when a new mission starts (`restarted`), or when the clock is null / the samples stop for more than 5 s; the next countdown starts a new mission with its own T0. History that starts mid-mission starts a `partial` mission (the step clock is all that is known). API: `new MissionClock()` with `add(t, tm, phase, mode)`, `clear()`, `missionTime(t)` (s or `null`), `toSample(tm, hintT)`, `covers(t0, t1)`, `dominant(t0, t1)` (the mission whose span overlaps the window most, used by the axis: a window with two missions uses ONE clock, that of the mission filling most of it), `missions` (`{ start, t0, t0Known, end, endReason, partial }`), `starts()` (`{ t0, end, endReason, partial, known }`, the T0 times with their ends); `buildMissions(samples)` is the pure function behind it. The graph axis (`web/app/plot/missionclock.js`: `missionAxis`, `fmtT`) uses it only while a mission is running in or ended less than 2 min before the window; otherwise (idle, no `MissionState`) the axis falls back to relative time (live: seconds before the window end, title "t (s, relative to now)"; replay: log time) and the info line's tooltip says so.
- **Cursor.** Live: hovering any graph moves one shared time cursor across all graphs and the legends show the values at the cursor; without hover the legends show the latest values. Replay: see "Replay". The x axis is mission time (see below), or relative time without a mission clock.
- **Second y axis** (`web/app/plot/axes.js`, tests `web/test/axes.test.js`). Each series of a graph sits on the left or the right y axis (`series.axis` "L" default | "R"; saved graphs without it stay left). In the Signals picker every selected signal has a small L / R toggle. A graph with a right-axis series gets a second axis on the right (coloured like its series when they share one colour) with its own rotated title ("Thrust [N]", or the units) and ticks, and the left axis is titled too; the grid belongs to the left axis. Each axis has its own auto / manual y range: "auto y" and "auto y R" with min / max boxes (the right one appears only with a right series), its own auto range from ITS series, and zoom / pan / reset: the right box zoom maps the same pixel box on both scales, the wheel zooms both manual axes about the pointer, left drag pans both manual axes, double click / Reset zoom / Back reset or restore both. Legends tag every series with its axis (a small L / R badge and the tooltip) when the graph has two axes, the header unit shows "left deg · right N". The ready-made **TVC** graph ("TVC deflection and thrust") shows the deflection angles on the left and `Actuators.thrust` (N) on the right; the other presets are unchanged (Thrust has one signal, Flaps one unit).
- **Replay** (`web/app/plot/replayview.js`, tests `web/test/replayview.test.js`). In the replay view the graphs always show the ENTIRE recording by default: on opening a log (or switching to the replay view) the panel loads all plot signals of the whole log once (`get_history` with `buffer: "plot"`, `whole: true`, `max_points: 20000` per series, `docs/api.md`: the core thins while reading, so a 10 minute log at 200 Hz is about 20000 points per series; the browser draws at most two points per pixel column as in live), keyed by log name and span, so a seek, scrub or playing does not reload and nothing is appended while playing. The x axis spans the log in mission time (relative log time without a mission clock). The **replay position is the primary cursor**: a thick vertical bar with a handle on every graph, and the legends show the values at the bar. Hovering with the mouse adds a second, thin dashed cursor; its values appear dimmed behind each legend value after "@" and the info line shows "hover <time>". Scrubbing: a left click on a graph seeks there, a left drag starting on the bar (within 6 px, the pointer shows a resize cursor) scrubs (seeks are throttled to one per 80 ms while dragging, the last one is sent at once; `replay.seek` moves the viewer only, as the transport slider does); the transport scrubber works as before. The window buttons are the zoom level in replay: **all** is the default (a remembered per-mode setting, `exgs.tuning.window.replay`; live keeps `exgs.tuning.window`), 10 s / 30 s / 2 min show a window of that length centred on the replay position (it follows the playing replay); box zoom, wheel and left-drag pan freeze the window as in live (the Pause button reads Follow) and Reset zoom, double click or a preset button return to the preset (the whole recording with `all`). Without an open log the panel says so. Browser test `test_browser_tuning_replay_shows_the_whole_log_with_a_position_bar`.
- **Performance.** Canvas, min/max decimation per pixel column (`web/app/plot/series.js`: 100 Hz over 2 min on 600 px is at most 1200 points per series), about 15 redraws per second only while the view is visible. Measured on the fake source (8 graphs, about 25 000 points drawn): about 1.5 ms per redraw. Browser tests `test_browser_tuning_graphs_live_history_reload_and_replay` (live, reload keeps history, pause, replay), `test_browser_tuning_box_zoom_pan_and_reset` and `test_browser_tuning_replay_shows_the_whole_log_with_a_position_bar`.

**Missing telemetry for tuning** (to be requested from the flight software; nothing is invented here): attitude setpoint (quaternion or angles) and attitude error; angular-rate setpoint; controller terms per axis (P, I, D contributions, integrator states, output saturation flags); commanded vs achieved thrust and torque (it is not documented whether `Actuators` is command or feedback); flap commands (`FlapState.cmd` is not sent by the vehicle); acceleration setpoint; estimator innovations / residuals (GNSS, baro, magnetometer) and covariance diagonals beyond att/vel/pos σ (gyro and accel bias σ); estimated linear acceleration; barometric altitude; task names and valid `max` values for `TaskTiming` (all NaN on the bench), loop period and jitter; battery voltage and current; motor RPM / ESC feedback; the mission plan (list of upcoming points, time to the next phase).

### Replay smoothness (owner report 2026-11-26, `feature/replay-smooth`)

The core pushes the replay position only with `status` (every 500 ms, `docs/api.md`). Measured before the change (300 s log, 8 graphs): status interval 500 ms, the bar was drawn from that value, so it advanced in steps (a 2 Hz stair); a full graph redraw cost 3.5 to 4 ms (decimation of every series plus drawing it) at up to 15 per second; a seek answers in 1 ms on the core, but the 3D view refetched the path on every seek. Changes (all in the GUI, no core change):

- **Playhead** (`status/replay_playhead.js`, pure, `web/test/replay_playhead.test.js`): the position shown by the transport, the graph bar and the events highlight is `ctx.replayPos()`, extrapolated from the last pushed position with the replay speed and `performance.now()`. A push corrects it gently (the error is absorbed over 0.5 s by a temporary rate change, never backwards); it snaps on pause, end, a state change, or an error above 1 s (log seconds, scaled by the speed). The position never leaves the log.
- **Cached series layer** (`plot/layercache.js`, `web/test/layercache.test.js`): each graph draws grid, axes and series to an offscreen canvas only when the layer key changes (size, devicePixelRatio, window, manual y ranges, axes labels, ticks, title, theme colours, data version = length and first/last time of each series). Every animation frame (`requestAnimationFrame`, one per frame) only blits the layer and draws the bar, the hover cursor and the selection box; measured 0.2 to 0.5 ms for all 8 graphs instead of 3.5 to 4 ms. Live graphs change window every frame and redraw as before. The legend values at the bar follow at most every 50 ms.
- **Scrubbing**: dragging the transport slider or the bar on a graph moves the local position and bar at once (`ctx.replaySeek(t, final)`); the `replay.seek` requests are throttled to one per 70 ms with the newest value always sent (`createCoalescer`, a trailing send) and the final one at once on release. Status pushes are ignored while dragging and for 300 ms after the final seek (a drag that never ends expires after 1 s). The 3D path refetch (replay "Path up to now") waits for 250 ms of quiet; meanwhile the old path stays (cut at the new position), the pose follows every seek. The ±5 s buttons and a click in the events list seek at once through the same helper. Measured: 121 slider events in 2 s (one per frame) gave 30 core seeks.

### Mission panel: mission time and phase time

`MissionState.t_mission` restarts with every step of the mission chain, so it is the time in the current phase, not since mission begin. The panel's **Mission time** tile and the time stamps of its "Phase changes" list show the continuous mission clock of `status/mission_clock.js` (T- in the countdown, T0 at mission begin, then continuous across all phases; a new mission starts a new clock, by the rules in "Tuning view", "x axis"; the phase list, the events sections `Mission N, begun at ...` and the optional clear at new mission follow the same missions). The old value stays as the smaller **Phase time** tile. Until a mission has been seen the Mission time tile shows an em dash (the phase time still shows the vehicle value). The clock is fed by `status/mission_time_display.js` (`MissionTimeFeed`: live MissionState packets, thinned like the events list; the history from the core's `get_events` after a reload or in replay, so the replay position maps to the right mission time). The status bar has no mission-time cell, and the callouts (countdown 5..1, mission start) keep reading the vehicle's `t_mission` countdown (they speak, they do not display a time). The 3D trail uses `t_mission` for logic only.

## Mission events (panel `events`, Bench Mission column; `status/mission_events.js`, `panels/events.js`)

A timestamp list of what happened when, display only (nothing is sent; the click-to-seek in replay moves the viewer, not the vehicle). Each row: **mission time** (the continuous mission clock of `status/mission_clock.js`: `T-` before T0, `T+` after, not the per-phase `t_mission`; `—` before the first mission started; after a mission's end it keeps counting from that mission's T0 until the next countdown), **wall time** (local, full date and time in the tooltip), a category icon, the text (`xN` = identical console/GS lines folded within 60 s) and the source packet type (tooltip). A new mission starts a section header `Mission N, begun at <time>` in the same list.

- **Replay:** when a log is opened the core reads the whole recording once (`get_events`, docs/api.md), so the list shows ALL events immediately; events after the replay position are dimmed (`upcoming`), the last event at or before the position is highlighted, **Follow** (remembered) scrolls to it, and a click seeks the replay to that event. A seek does not reload the list.
- **Live:** the list grows with the packets; after a page reload or reconnect it is restored from the core's buffer (newest 40000 kept packets) and continues.
- **Clear (live only):** the **Clear** button hides every event up to the newest one now. It is a display cutoff time (`applyCutoff` in `status/mission_events.js`), kept in the browser (`exgs.events.clear_t`) so a reload does not bring the old events back. The derivation still sees all events, so mission time stamps and dedupe stay right; only the list and the CSV export are cut. A mission header stays while later events of that mission remain and goes when its whole section is hidden. **Show cleared (N)** / **Hide cleared (N)** restores or re-hides them for the session. New events after the clear show normally. **Clear at new mission** (remembered, default off) sets the cutoff just before each newly begun mission's first row (countdown start) while the page is live; a reload or reconnect never auto-clears. In **replay** the button is disabled (tooltip: the log is not changed, nothing to clear) and the cutoff is ignored, so every recording opens complete.
- **Filter and export:** category checkboxes Mission / Vehicle / Command / Link / Log (remembered in the browser), **Export CSV** of the filtered events (`mission_time_s, mission_time, wall_time_utc, category, text, mission, source_type`; text cells starting with `= + @ -` get a leading apostrophe against spreadsheet formula injection). The list is virtualised (fixed row height, only the visible rows are in the DOM), so thousands of events are fine.

Events and their sources (one stateful deriver, the same code for the whole recording and the live stream; it reacts to a VALUE CHANGE, so repeated identical states give nothing and two sources reporting the same change within 3 s give one event; the first value seen is a silent baseline except armed, motors enabled, simulation, failsafe, set failure bits and the vehicle mode, marked "(state at start of data)"):

| Category | Event | Source |
|---|---|---|
| mission | countdown start, mission begin (T0), mission end (Completed / reset to Idle / clock lost), already running when the data begins | mission clock over `MissionState` |
| mission | mission phase change, mission mode change, mission index and waypoint change | `MissionState` |
| vehicle | vehicle mode change, armed / disarmed, motors enabled / disabled (the vehicle's gate), simulation on / off, failsafe set / cleared, ready to arm, each failure bit set / cleared (named as in the status bar), vehicle flags (ABORT latched, FAILSAFE latched, ... warn/bad bits of `ctrl_flags`), degraded bits | `VehicleStatus` |
| command | what the GS sent: GO (SA), profile (SB), SIMULATION/REAL (SC), motors armed / disarmed (SD), SE pressed / released, GS failsafe requested / cleared, command session start, Pocket stream live / lost, input virtual / Pocket | `CmdState` (the GS's own recorded command state) |
| command | what the vehicle applied (same fields), control source change, mission profile latched, go refused (with the reason), lease events, requests sent / ACK / timeout (`REQUEST_ACK ... DONE` lines), the engine's `ABORT sent` / failsafe lines | `CmdApplied`, `VehicleStatus`, `GsEvent` |
| link | source up / down, ship-node / Router link warnings and the vehicle losing the GS (`gs_present`, degraded bits 1 and 2) | `GsEvent`, `VehicleStatus` |
| log | recording start / stop, operator notes, vehicle console lines: bellyflop kick started / finished, RTH descent starts, landing declared, and everything `callouts/log_patterns.js` classifies (WARNING / ERROR lines, refusals, calibration, countdown abort) | `GsEvent`, `Note`, `ConsoleText` |

Limits: the telemetry carries the current mission step only, so "waypoint reached" is the reported waypoint or index changing, nothing more. `CmdApplied` exists on USB only. The core reduces the packets (`core/event_history.py`, a data reduction, not an interpretation); a recording with more than 100000 kept packets is cut and the status line says so. To show the panel elsewhere add `{"panel": "events"}` to a group of the layout (for example a second group of the Tuning view; a panel can be in one place per view only, and not in a group and the dock at once). It is not in the shipped Tuning view or the dock.

## Command panel (replaces "RC applied")

Panel `command` (`web/app/panels/command.js`, logic in `web/app/command/command_logic.js`, `web/test/command_logic.test.js`), Operations dock tab "Command" next to Radio. **Display only**: it sends nothing, and its two halves are labelled apart so the sent state is never read as the applied one.

- **Sent by the ground station (command engine)**, from the `rc` push (`command`): the session (32 bit and low 16 bits), the input (Pocket / virtual panel / none), the Pocket stream state (not seen / live / LOST), the command stream and its links (`sending to usb, router (25 Hz)`, or `NO COMMAND LINK CONNECTED`), the sent state (`go`, profile, REAL / SIMULATION, motors armed / disarmed, SE, failsafe), `NOT MASTER` and `MULTI_MASTER` when the vehicle reports them, and the pickup hints.
- **Applied by the vehicle** (`CMD_APPLIED`, port 0x84, USB only, so it has data only on a direct USB connection to the vehicle): the last accepted `go`, profile, vehicle mode (the field, not the applied mode), motors armed / disarmed, SE, failsafe request, the information flags (`POCKET_LIVE`, `INPUT_VIRTUAL`), the latched session, the four safe-value-seen bits (GO, SC real, SD armed, SE press), the age of the last accepted `CMD_STATE` (either link, USB, UART) and the four wrapping reject counters (bad length or field, source not node 0, foreign session, stale or duplicate). Used to compare every Pocket and virtual switch with what the vehicle decoded.

The status bar cell **Command source** (key `ctrl_source`, replaces "Control source") shows the vehicle's `ctrl_source` (GS or NONE), the latched session (low 16 bits of `VEHICLE_STATUS.cmd_session`, hex), `NOT MASTER` (red) when that session is not this core's, `MULTI_MASTER` and `GS_FAILSAFE_REQ` (red), and which links are fresh (`USB fresh`, `UART fresh`, `USB+UART fresh`, amber `no link fresh`). `NOT MASTER` is display only: the engine keeps sending and the vehicle decides.

**Mission profile names.** Wherever a mission profile number is shown it is followed by its name (pure `command/profile.js`, `web/test/profile.test.js`): 0 `hover test`, 1 `waypoint test`, 2 `flight`; 255 (none) shows nothing. Used by the status bar Profile cell, the Command panel (SB profile, Sent state) and the command path list; the SB meaning text in `config/radio.pocket.toml` (radio widget and virtual Pocket) lists the three names. The vehicle logs `GO: mission begin, profile N (name)`.



### Simulation testing page

Page `simtests` (`web/app/simtests/`: `simtests_panel.js`, sections `simwind_*` and `simfaults_section.js`, logic `simtests_logic.js`, `simwind_logic.js`). Greyed out and labelled 'simulation mode only' unless the vehicle itself reports simulation mode, in the live view, on a control host with a route. **Wind**: Apply wind (hold 1 s) sends `SIM_WIND_SPEED`, `SIM_WIND_DIRECTION`, `SIM_GUST_STRENGTH`, `SIM_GUST_PERIOD`, `SIM_GUST_SEED` as requests one after the other, each after the vehicle's ACK, stopping at the first refusal; Clear wind sends speed 0 and gust 0. **Servo faults**: Force flap, Apply slow servo and Release all faults are one request each after a 1 s hold. The result of each request is the vehicle's ACK in plain words (for example 'refused: the vehicle is not in simulation mode'). Pacing and wording: [requests.md](requests.md).

### Mission parameters (rows of the Vehicle panel, feature/mission-params)

The Vehicle panel's stop altitude control became one table, "Mission parameters" (`web/app/vehicle/missionparams_logic.js`, `web/test/missionparams_logic.test.js`, panel code `vehicle_panel.js`). Groups: "Flight (profile 2)" (ascent speed 0.5..10 m/s, ascent acceleration 0.2..20 m/s^2, ascent deceleration 0.2..20 m/s^2, `Apogee position X (north) m` and `Apogee position Y (west) m` -2000..2000, `Apogee altitude Z (up) m` 2..1000, and the stop altitude, at least 1 m, which keeps its own request SET_STOP_ALTITUDE), "Hover test (profile 0)" (hover hold 0..600 s) and "Waypoint test (profile 1)" (hold 1, 2, 3, 0..600 s). Per row: an input (min and max from the range, validation text `allowed: 0.5 to 10 m/s` beside it), `vehicle: 7.0` (the readback from `MISSION_PARAMS`, the stop altitude from `MissionState`; `vehicle: unknown` until it arrives) and the result of the last send in words. Untouched inputs show the vehicle's value (the default while unknown); edits are kept until sent, and an input that has been sent follows the readback again.

**One Send** (label `Send (n)`) sends every field whose valid input differs from the vehicle's value (an edited field while the vehicle value is unknown also counts); it is disabled when nothing changed, an input is invalid, the view is replay, there is no control host or route, or a sequence runs. The requests go **one at a time**: each waits for its ACK (new `req_id` per field, up to 7 s, else `no answer from the vehicle`), the next starts 550 ms later, also after a refusal. Row results: `set` (green), `refused: motors armed or in flight`, `refused: session mismatch, ...`, `refused: value out of range`, `no answer from the vehicle`, `not sent: <core reason>`; the stop altitude keeps its echo cross-check (`set` only when `MissionState.stop_altitude` matches). A one-line summary follows (`all 4 parameters set`, `1 of 3 set, 1 refused`). **Reset to defaults** (small link) fills the inputs with the defaults and sends nothing. Note shown: "accepted only on the ground, motors disarmed; a vehicle reboot returns the defaults". An apogee altitude input below 90 m shows `below 90 m: no bellyflop, the flight ends in RTH`; an apogee X or Y input with an absolute value above 0.5 m shows `apogee not above home: the descent flies a lateral transfer to home`. The old `stopalt_logic.js` stays for the stop altitude wording and echo check. Tests: JS logic (changed-field detection, paced sequence, row results, reset, warning) and one browser test in `tests/integration/test_ops_gui.py`.
