# GUI: structure, views, panels, 3D view (design section 5)

Redesigned on `feature/gui-redesign` (user request 2026-11-20): views by usage instead of devices, the main groups Vehicle, Guidance and Mission left to right with the 3D view in the centre, one Operations dock for everything that is setup or diagnostics, a data-source tag and recording controls on every page, and a new dark theme with a high-contrast light option. Spec: [ground-station-design.md](ground-station-design.md) section 5. Screenshots (fake source): `docs/img/bench-1920.png`, `bench-1366.png`, `flight-1920.png`, `flight-1366.png`, `tuning-1920.png`, `tuning-1366.png`, `replay-1366.png`.

Plain ES modules in `web/`, served by the core (`GET /`, `/static/...`). No build step, no CDN, works offline (Three.js 0.170.0 is vendored in `web/vendor/three/` and resolved by the import map in `index.html`). Checked in a real headless Chromium by `tests/integration/test_gui.py` and the other `test_*_gui.py` / `*_widget.py` tests.

## Page structure

From top to bottom, identical in every view and in live and replay:

1. **Data-source tag** (`status/source_banner.js`, logic `status/source_logic.js`, unit tested in `web/test/source_logic.test.js`; user request 2026-11-20: a small pill, not a full-width banner). It leads the vehicle status row under the header, colour-coded, the tooltip gives the full text:
   - **REAL** (green) when the freshest `VehicleStatus.simulation` is false, **SIMULATION** (violet) when it is true;
   - **REAL / SIM ?** or **REAL? stale** / **SIM? stale** (amber) when no `VehicleStatus` arrived, the flag is not supplied or the packet is stale (never assumed);
   - **REPLAY** (blue), **NO CORE** (red) while the WebSocket is down.
   In the replay view a compact **replay strip** under the status bar shows the log name, the position `mm:ss / mm:ss`, playing/paused/ended, **recorded: REAL / SIMULATION / unknown** (from the replayed `VehicleStatus.simulation`), the transport (play/pause, scrubber, ±5 s, speed, keyboard space and arrows) and the small note **🔒 replay: inputs locked**. The status bar cells do not repeat the simulation flag.
2. **Header** (`header.js`): the layout views **Bench / Tuning** (Alt+1, Alt+2; remembered in `localStorage` `exgs.view`), the data view **LIVE / REPLAY**, the **command chip** (what the core's command engine reports: `CMD SENDING · POCKET`, `CMD SENDING · VIRTUAL` in amber, `CMD SENDING · IDLE`, `CMD NO LINK · ...` in red when no command link is connected, `· POCKET LOST` appended on a Pocket loss; click opens the radio tab), the radio link quality, the **recorder block** and the core connection and theme switch (dark default, light high contrast, `exgs.theme`).
   - Recorder block (status from `status.recorder`, logic `describeRecorder`): idle shows `not recording`, the free disk space (amber below 5 GB, red below 1 GB) and **● Record** (starts a recording at once, manual only). Recording shows a pulsing red **REC mm:ss**, the log name, its size, free space and a red **■ Stop** button (no confirmation). Recorder errors and dropped packets are shown in red. Labels, notes and the log list stay in the dock tab Recordings.
3. **Mission status bar** (`status/status_bar.js`, unchanged logic, see below). New: a red **TX POWER** line when any transmit power (LinkConfig, TxModuleStats, RxModuleStats) is above 10 dBm, so the warning is visible whichever dock tab is open (stale values stay listed and are marked).
4. **Workspace**: the view's groups (`#panels`) and the Operations dock (`#dock`) on the right.

## Views and groups

| View | Groups (left to right) | Dock | Purpose |
|---|---|---|---|
| **Bench** (default) | Vehicle: attitude, position & velocity, actuators (all compact), GNSS, health · Guidance: 3D view (full height) · Mission: mission (compact), target vs current (compact), data rates (compact) | open | everything, for bench work and setup |
| **Tuning** | Graphs: the tuning graph workspace | side rail | time-series graphs for filter and control tuning |

The **Tuning** view is described in "Tuning view" below. The old `default` and `phone` presets and the device idea are gone; a narrow window (below 1100 px) stacks the groups in one column and the page scrolls (no horizontal scroll at 390 px, tested).

**Why this arrangement.** The reading order is Vehicle → Guidance → Mission. The 3D view shows ship pose, target, trail, flaps and thrust together, which is above all the guidance picture (where the vehicle is against where it should be), so it heads the centre column and is the largest element; the numeric target-vs-current table sits right under it. Vehicle state (the inputs to guidance) is on the left, the mission (what guidance follows) on the right. Inside each group the most important values come first as big tiles with units (attitude angles, altitude and speeds, thrust and TVC; distance and errors to target; phase and mission time), then tables, then details and hints. Safety-relevant states (REAL/SIMULATION, replay, armed, motors, failsafe, failures, RC master, transmit power) are in the data-source tag, header and status bar, never only inside a panel; panels do not repeat them (the old `modes` panel is removed).

**Operations dock.** Tabs: Radio, Command (CMD_APPLIED and the engine's report, see below), Requests, Commands (temp), Simulation testing (simulation-only wind and servo-fault commands (Force flap forces a flap's setting to an angle at once; Release all faults), hold 1 s, greyed out unless the vehicle reports simulation mode, [telecommands.md](telecommands.md)), Link & power, Recordings, Raw sensors, Console, Inspector (`role=tablist`, arrow keys). In Bench it is a column (440 px, 380 px below 1500 px), collapsible to the rail with ⟩ (remembered per view, `exgs.dock.<view>`). In the rail (Flight) the tabs are vertical labels; a click opens the dock as an overlay over the groups (✕ or Escape closes it). The Console tab shows the number of new WARNING/ERROR vehicle lines since it was last open, and the header shows an amber calibration chip while the vehicle reports invalid calibration (both from the log watcher, [callouts.md](callouts.md)). The Failures panel (Vehicle group) also shows three calibration rows, Gyro, Accel and Mag, and a small row Ready to arm. **Primary source: the vehicle's structured `VehicleStatus.calib_state`** (decoded to `calib_gyro_ok`, `calib_accel_ok`, `calib_mag_ok`, `ready_to_arm`; used while VehicleStatus is fresh): green ok, red INVALID; the vehicle's log text only supplies the reason as the note (`last run failed`, `parameters out of range`, ...). **Fallback** when the vehicle sends no `calib_state` (older sender, value 0): the log text decides alone, as before (`LogWatcher.calibState()`), grey `—` when the vehicle has not said anything. Ready to arm is green `ready` or red `NOT ready` from `ready_to_arm`, grey `—` when unknown (no banner, no log fallback). All in `web/app/status/calib_rows.js`. A small line `Arm and MissionBegin are refused until calibrated` appears while any row is red. Display only. A tab shows a marker dot: amber while the core reports RC master, red with "Pocket also active", red/amber for a transmit power problem. **Dock panels are mounted once and survive a view change**, so switching Bench ↔ Flight does not destroy the radio widget and does not release a held RC lease (before the redesign a preset change destroyed the panel and released the lease; see the report: user decision). In replay, and without a connection, the input tabs (radio, requests, commands) show the line "replay: inputs locked: nothing can be sent from here" above the panel; the panels are now shown disabled in replay (each button disabled with its reason) instead of being hidden. Their guards are unchanged (hold to confirm, danger modal, locks, rate limits, the core's own refusal).

## Layout file

`config/layout.default.json` (served at `/config/layout.json`, path set by `[gui] layout`), validated by `web/app/layout.js` (`normalizeLayout`, unit tested):

```json
{ "default": "bench",
  "dock": { "title": "Operations", "tabs": [ { "panel": "radio", "label": "Radio" } ] },
  "views": { "bench": {
      "label": "Bench", "hint": "tooltip text",
      "columns": "minmax(250px, 1fr) minmax(320px, 1.55fr) minmax(220px, 0.85fr)",
      "dock": "open",
      "groups": [ { "id": "vehicle", "title": "Vehicle",
                    "panels": [ { "panel": "attitude", "collapsed": false, "options": { "compact": true } } ] } ] } } }
```

- `columns` is a CSS `grid-template-columns` for the groups (one column per group, in order). `dock` is `open` or `rail`.
- `options` are passed to the panel as `ctx.options`: `compact` (attitude, position, actuators, targetvs, mission, rates: fewer rows), `height` for `view3d` (`large`, `fill`).
- A panel is either a dock tab or in the groups, never both; unknown panels, duplicates and empty groups are reported in the browser console and dropped; with no valid view the fallback is one group with every panel. A remembered view that no longer exists (for example `phone`) falls back to the default.
- Collapsed state per view: `exgs.collapsed.<view>`. All storage access is wrapped in try/catch.

## Visual design

Tokens in `style.css` (`:root[data-theme=dark|light]`): surfaces, lines, text, the meaning colours (green ok, amber warn, red fault/danger, blue info, violet simulation) and the data-source tag colours; graphs will use the eight validated categorical series colours `--s1..--s8`. Type scale 11/12/13/15 px, tiles 21 px (28 px in Flight), hero 26 px (34 px in Flight); numbers in a monospace font with tabular figures. Number formats: angles 1 decimal in degrees, rates deg/s 1 decimal, positions and velocities 2 decimals (m, m/s), σ 2 decimals; units are always shown (tiles next to the value, tables in a unit column). Stale values are dimmed and struck through with their age (tiles hide the age, the panel badge shows it), missing values `—`, not supplied `n/s`.

## Behaviour

- **Connections.** The shell opens one WebSocket (mode `latest`, 20 Hz) for all panels with mode `latest`, and a second one (mode `all`) only if a mounted panel has mode `all` (the console). Subscription types are the union of the mounted panels' `consumes`; `"*"` (inspector) subscribes to everything. Only the active view is subscribed. After a reconnect the core sends a `snapshot` and the store is rebuilt.
- **View clock.** Ages are computed against the view's clock from the core (`clock` in `status` and `packets`), extrapolated with the browser's monotonic timer between messages, never the browser's wall clock. In the replay view the clock is the replay position: frozen while paused or ended, running at `speed` while playing.
- **Freshness per value (`fmt.describe`).**
  - `fresh`: normal text.
  - `stale`: older than the entry's `stale_after` (schema nominal rate if missing, else 2 s). Dimmed and struck through with an age badge. The last value stays visible.
  - `missing`: no packet of that type in this view. Shown as `—`.
  - `not supplied`: the packet arrived but the field was not in it (reduced radio set). Shown as `n/s` in italics.
  - Every value carries a small source tag (`usb`, `link`, `fake`). Values are merged field by field over all sources (user report 2026-11-22: values flickered between a number and `n/s` with the Router next to the USB): each field comes from the highest-priority source (`core.source_priority`) whose packet is fresh and carries it, else from the newest packet that carries it, with the field's own source tag and age and its own stale threshold (`web/app/store.js` `Store.get` without `src`, `describe()` in `fmt.js`). A field no connected source carries shows `not sent` (tooltip: not sent by the vehicle, with the sources checked), `n/s` with a single source; the table is in [field-sources.md](field-sources.md). Per-source access (`store.get(view, type, src)`, the inspector, the data rates panel) is unchanged. The inspector lists every (type, source).
  - Derived values (roll/pitch/yaw, tilt, vector to target, distance) use the oldest of their inputs for freshness and join the source tags.
  - Each panel header shows `stale <age>` or `no data` for the worst of its values.
- **Vehicle-reported values only.** Panels never show anything inferred from commands that were sent. Derived values are display-only arithmetic on received data and are labelled as such.

## 3D view

Panel `view3d` (the Guidance group in Bench, full height). It consumes `Attitude`, `Position` (ship pose, trail), `MissionState` (setpoint), `FlapState` and `VehicleState` (`tvc_thrust`). Everything comes from the store, so it works the same live and in replay.

**Frames** (`view3d/frames.js`, tested in `web/test/frames.test.js`):

- World: NWU (X North, Y West, Z Up). Three.js is Y-up. All vehicle content sits under one `worldRoot` group with `rotation.x = -90 deg`, which maps NWU `(x, y, z)` to Three.js `(x, z, -y)`: North is +X, West is -Z (East +Z), Up is +Y. Inside `worldRoot` positions are NWU metres and the attitude is the vehicle quaternion.
- Quaternion: the vehicle `q = [w, x, y, z]` (body to world) becomes `quaternion.set(x, y, z, w)` after normalising. A norm that deviates by more than 1 % shows "invalid attitude" (ship drawn as a ghost).
- Body frame: right-handed, +Z the long axis with the nose toward +Z, the belly faces -X (South with the identity attitude), the back +X. The flaps TL and BL are on the +Y side, TR and BR on -Y. Flap angle 0 is fully extended along +-Y, increasing angle folds the flap toward +X (the back), 90 deg is folded flat. Source: workspace `docs/system-architecture.md`, "Vehicle geometry and body frame". The ship carries a dark strip on the belly as an orientation cue.

**Scene.** Ground grid at z = 0 (1 m cells, 10 m major lines, +-50 m), axes gizmo at the origin with N, W and Up labels, a 5 m compass ring with N/W/S/E, the ship, the trail (last `trail_window_s`, default 60 s, fading with age), the setpoint (ghost sphere with crosshair at `MissionState.sp_pos`, a dashed line from the ship, an arrow for `sp_vel` of 1 m per m/s), and a thrust arrow along `VehicleState.tvc_thrust` (body frame) ending at the tail, scaled by `thrust_arrow.m_per_n` up to `max_m`. Optional body axes (checkbox). Target attitude (checkbox "target attitude", default on): see below. Cameras (OrbitControls): Follow (orbits the ship), Observer (orbits the origin), Top (North up, zoom only).

**Data rules.** The ship needs both attitude and position, and is not drawn without them ("no attitude and position data"). If either is stale it is drawn semi-transparent with a "stale <age>" label, never extrapolated. With no `FlapState` in the view all flaps show `default_flap_angle_deg` (45 deg) and the overlay and the actuators panel say "flap data: none (default 45 deg)". Stale flap data keeps the last angles with a "flaps stale" label. The flaps jump to the reported angle, no smoothing. The trail is loaded with `get_history` on connect, on a view change and on every snapshot (so after a replay seek), then extended with live `Position` packets from the source that is currently preferred; a sample older than the last one resets it.

**Model config** (`config/model.<name>.json`, set by `[gui] model`, served at `/config/model.json`, files in `models/` at `/models/`). The placeholder is a procedural ship with the owner's real dimensions (2026-11-21, all named in `dimensions_m` of the config, metres, measured from the bottom of the ship): tube 13 cm diameter and 54 cm high, parabolic nose 20 cm high on top of the tube (total 74 cm), origin on the axis at the centre of mass in the middle of the ship (37 cm from the bottom, so the tube ends at z = +0.17 and the nose tip is at z = +0.37). Top flaps 7 x 14 cm with the lower edge 53 cm from the bottom (pivot z = +0.23), bottom flaps 8 x 21 cm with the lower edge 1 cm from the bottom (they span 0.01 to 0.22 m above the bottom, pivot = flap centre at 0.115 m, z = -0.255), 8 cm chamfer on the top (nose side) of every flap. Extended flaps (angle 0) lie in the Y-Z plane through the axis, not swept, hinge parallel to the axis on the tube surface at y = +-6.5 cm. The top flaps start 1 cm below the tube end, so most of their length sits beside the nose. The top flaps are tilted inward by `dimensions_m.top_flap_cant_deg` (10 deg, per-flap `cant_deg`, positive = upper end toward the axis) about their lower hinge point (pivot minus half the flap length, so the lower point stays on the tube and the upper end moves toward the axis by about length x sin(cant), 2.4 cm for the top flaps). The deflection angle (0 = extended, increasing = folded toward the back) applies on top of the cant, about the tilted hinge. The flight simulator uses the same names and values.

```json
{ "name": "placeholder",
  "body": { "source": { "primitive": "starship-placeholder", "height_m": 0.74, "radius_m": 0.065,
                        "nose_length_m": 0.20, "origin_from_bottom_m": 0.37 },
            "model_to_body": { "rotation_deg_xyz": [0, 0, 0], "translation_m": [0, 0, 0], "scale": 1.0 } },
  "flaps": [ { "id": "tl", "index": 0,
               "source": { "primitive": "flap", "width_m": 0.07, "height_m": 0.14, "thickness_m": 0.004,
                           "chamfer_m": 0.08, "chamfer_corner": "out_top" },
               "model_to_body": { "rotation_deg_xyz": [0, 0, 90], "translation_m": [0, 0.065, 0.23] },
               "pivot_body_m": [0, 0.065, 0.23], "axis_body": [0, 0, 1], "sign": -1, "model_angle_deg": 0 } ],
  "default_flap_angle_deg": 45,
  "thrust_arrow": { "m_per_n": 0.02, "max_m": 0.6, "origin_body_m": [0, 0, -0.37] },
  "trail_window_s": 60 }
```

- `source`: `{ "primitive": name, ...parameters }` (`starship-placeholder`, `flap`) or `{ "gltf": "models/ship.glb", "node": null }`. With `node` set, that node of the file is used (its own transform in the file is ignored) so the body and the flaps can be nodes of one file or separate files. Both go through the same loader and the same transforms.
- `model_to_body` (body and, as an extension of the design, each flap): rotation as Euler XYZ in degrees, translation in metres, uniform scale, mapping the model's own frame into the body frame **at the modelled angle**. glTF is Y-up, so a glTF ship with its long axis along Y needs `[90, 0, 0]` (glTF Y goes to body Z, glTF Z to body -Y). The primitives are built directly in the body frame.
- Flaps: `pivot_body_m` and `axis_body` (body frame, unit vector) define the hinge. The pivot group rotates by `sign * (angle - model_angle_deg)` about the axis, `angle` in the vehicle convention and `model_angle_deg` the angle at which the flap is modelled in its file. `index` selects the element of `FlapState.angle` (0 tl, 1 tr, 2 bl, 3 br).
- Placeholder flap plate: hinge on the model's Z axis, the plate extends toward +X, `chamfer_m` is the length of a 45 deg cut at the outer corner named by the orientation parameter `chamfer_corner`: `out_top` (toward the nose, +Z) or `out_bottom` (toward the tail). **All four flaps use `out_top`** (user decision 2026-11-20: the bottom flaps were drawn upside down with the chamfer at the bottom); a flap that is modelled the other way up is fixed by this one parameter in its config entry, never by rotating it. The architecture note gives only "8 cm chamfer"; the 45 deg cut is an assumption of the placeholder and, like the corner, changes by config only. The pivot is at the flap's vertical centre on the body surface at +-Y (z = +0.23 m top, -0.255 m bottom; the top flaps span z = +0.16 to +0.30 m, the bottom flaps z = -0.36 to -0.15 m, before the cant of the top flaps).

**Swapping in a real glTF model** (config change only, no code):

1. Put the file in `models/` (for example `models/starship.glb`) and copy `config/model.placeholder.json` to `config/model.starship.json`.
2. Body: `"source": { "gltf": "models/starship.glb", "node": "hull" }` and `model_to_body` so that the model's nose points to body +Z, the belly to -X and the origin sits at the centre of mass (glTF Y-up long axis: `rotation_deg_xyz: [90, 0, 0]` plus a translation if the file's origin is elsewhere).
3. Flaps: either `{ "gltf": ..., "node": "flap_tl" }` per flap or separate files. Set `pivot_body_m` to the hinge in the body frame, `axis_body` and `sign` so that increasing angle folds toward +X, and `model_angle_deg` to the angle the flap has in the file (0 if modelled extended). Check with the checkbox "body axes" and by watching the flaps move.
4. Set `[gui] model = "config/model.starship.json"` in the core config and reload the page. A config that fails validation, or a model that fails to load, shows "3D view unavailable: ..." in the panel, and the rest of the GUI keeps working. Run `.venv/bin/pytest tests/integration/test_view3d.py` to re-check the loader with `models/test-box.gltf`.

**Target attitude (display only).** The vehicle's attitude setpoint `MissionState.sp_q` (quaternion body to world, NWU, from `MISSION` / `AIR_MISSION`) is drawn as three thin dashed, semi-transparent "ghost" body axes (X red, Y green, Z blue, the colours of the real body axes) at the ship position, with the same conversion as the ship (`vehicleQuatToThree`, `view3d/frames.js`), so they coincide with the real axes when the vehicle tracks perfectly. They are hidden when `sp_q` is None (all four zero, NaN from an older sender, or a link without it), stale or unusable, and with the checkbox off. The overlay reads "attitude error (setpoint vs estimate): N.N°", the shortest-arc angle between `Attitude.q` and `sp_q`. No smoothing, nothing sent to the vehicle. Note: the vehicle's flap controllers only control the direction of body +Z, so during bellyflop and freefall the published setpoint roll follows the real roll: the error then shows only the pointing error, not roll.

**Target smoothing (display only).** The target sphere shown in the 3D view is smoothed: it is **not** the raw reported `sp_pos`. It is a critically damped second-order follower (time constant 0.25 s) of the reported `sp_pos` with feed-forward velocity (`view3d/target_smooth.js`, tested in `web/test/target_smooth.test.js`). Between packets the follower's goal is extrapolated with the target velocity, but never beyond one packet interval plus 50 ms (1.25 x the measured interval + 0.05 s, at most 0.5 s), then it holds. The velocity is `sp_vel` when it agrees with the difference of consecutive `sp_pos` values, else that difference, because `sp_vel` is not the derivative of `sp_pos` in every phase (in the recorded run it is 0 while `sp_pos` moves 5 m/s in Deceleration and 0.2 m/s in Landing). A jump between two packets implying more than 30 m/s is a guidance step (phase change, waypoint): the display glides to the new position within about a second instead of teleporting, and no velocity is derived from it. A continuous motion is followed without lag. The follower runs on the view clock (packet arrival, the packets carry no own timestamp), resets on replay seeks, view changes and stale MissionState. Panels and plots keep the raw vehicle-reported `sp_pos` and `sp_vel`; nothing is sent to the vehicle. Evidence and numbers: `tools/analyse_target_smoothing.py` on a recorded run (USB 20 Hz and a simulated 5 Hz radio path with 1 mm / 0.01 m/s quantisation and jitter): visible stutter (change of the per-frame displacement) at 5 Hz p99 / max 5.2 / 98 mm with the previous extrapolation + 150 ms blend versus 2.0 / 14 mm now, and the per-frame jump at a guidance step 7.3 m versus 0.47 m.

**Debug hook** for end-to-end tests: `window.exgs.view3d.debug()` returns the ship pose and visibility, nose, belly and origin in Three.js coordinates, per-flap angle and outer-edge position in the body frame, flap source (`data`, `default`, `stale`), setpoint and thrust visibility, trail point count, overlay text and camera mode. `window.exgs.view3d.scene3d` gives the Scene3D object.

## GNSS panel and altitude cross-check

Panel `gnss` (`panels/gnss.js`, logic in `gnss/gnss_logic.js`, unit tested in `web/test/gnss_logic.test.js`). Vehicle-reported values only; the cross-check compares two reported values and **sends nothing**: it never changes anything on the vehicle and is never the only warning. Data: the `Gps` packet, which is the USB `GNSS` (0x83, all fields) or the radio's `AIR_GNSS` (10 Hz position and velocity) merged by the wire profile with the 1 Hz `AIR_GNSS_INFO` (`docs/wire-profiles.md`).

- **Content (compact, no scrolling).** Latitude / longitude in degrees (7 digits) on one row, absolute GNSS altitude (the receiver's altitude: u-blox height above the WGS-84 ellipsoid, not above sea level), the velocity in NED (N, E = -W, D = -U), tiles for satellites, fix type name and the altitude cross-check status, and tiles for the receiver's own accuracy estimates (1 sigma): horizontal, vertical and speed (`vel_acc`, USB GNSS only, "—" otherwise). Without a fix (`None` values) the panel shows "—" and "no fix", never stale numbers as current. Panel `radio` (`web/app/radio/`; first tab of the Operations dock). **Safety-relevant**: it is the GUI's **virtual Pocket**. Since the GS-control cutover the core's command engine is the only sender of vehicle commands and runs without any client ([radio.md](radio.md)); the widget only feeds the engine the virtual switches while this client holds the panel lease and the Pocket is not live (the real Pocket wins). Rules, enforced in `radio_logic.js` / `radio_widget.js` and covered by the tests:

- **Always the core's state.** Every control, the µs readout and the banner come from the `rc` push messages (the panel's state; what the vehicle applied is in the Command tab). A click sends a request (`rc.set`) and changes nothing locally; the control moves when the core reports it. The one exception is the slider thumb while it is being dragged.
- **Config driven.** The controls, their kinds, positions on the handset (`svg = {x, y}`), labels and `meaning` tooltips come from `config.get radio`. SD is labelled "motors armed / disarmed".
- **Banners** (from `rc.mode`, `rc.command`, `holder_is_you`, connection and view): a chip `VIRTUAL` (amber) / `POCKET` (blue) / `IDLE`, and the banner: `VIRTUAL · input of the command engine · command stream 25 Hz to <links>`, `POCKET live · input of the command engine · ...`, `NO INPUT · the core holds its last command state`, `NO COMMAND LINK CONNECTED` when the engine has no connected command link, `VIRTUAL (<holder>)` for another client's lease, red `DISCONNECTED · the core keeps sending its command state without the GUI`, violet `REPLAY`. A red **warning** banner: `WARNING: Pocket stream lost. The ground station keeps sending its last command state (SE released); after the Pocket returns, a switch in an unsafe position must be cycled first` while the engine reports the Pocket lost (a toast is raised from the core's event as well; no abort and no failsafe is sent), and `The Pocket is the input: the virtual switches are inactive while it is live` while the panel is held but the Pocket is live. An amber **pickup hint** box lists what the input waits for: `SA is up while go is off: flip it down first`, the same for SD (motors disarmed) and SE, and `SC: flip to REAL (position 0)` / `SIMULATION (position 1 or 2)` to take over. The buttons are "Use virtual switches" (`rc.acquire`) and, for the holder, "Release virtual switches".
- **Operable only while this client holds the lease, the core reports `virtual` and the Pocket is not live.** Otherwise all controls are read-only (idle, Pocket live, someone else holds the panel, disconnected, replay). "Use virtual switches" is enabled only when the core said this client may control (`welcome.can_control`), the view is live and nobody holds the lease; it is **also available while the Pocket is live** (it then has no effect until the Pocket stops). A new holder starts at what the engine is sending (the panel is preset to the output: SD shows armed with its guard open if the motors are armed), so taking the panel changes nothing that is sent.
- **Heartbeat** `rc.heartbeat` every 300 ms while this client holds the lease. Closing the tab or losing the connection ends the lease at once (WebSocket close), a stalled page within 1 s: the panel returns to its defaults and the **engine keeps sending its last command state** (it needs no client). After a reconnect the client does **not** take the panel again by itself.
- **Controls.** `toggle2`: click flips. `switch3`: click the top, middle or bottom zone, or arrow keys / space (SC: position 0 = REAL, 1 and 2 = SIMULATION). `momentary` (SE): `SE=1` on pointerdown and every 100 ms while held, `SE=0` on pointerup, pointercancel, lost pointer capture, window blur and when the page is hidden (the core also releases it 300 ms after the last refresh; the engine stretches a press to at least 160 ms). `slider` (S1): display only.
- **Padlock.** A control with `lock` in the radio config (SD, motors armed) is shown as a padlock while the core reports it locked: hold it for 1 s (progress bar) to send `rc.unlock`. While unlocked the switch is operable and shows `unlocked · <seconds>`, with a Relock button (`rc.lock`, back to disarmed). When the core relocks it (timeout, lease end) the padlock returns on the next push.
- **Replay.** In the replay view the widget shows the recorded `RcState` read-only under the REPLAY banner. Switching to replay while this client holds the panel asks "Release control and switch to replay?" (in-page dialog); the release is sent before the view changes.
- **Sticks (display only).** Under the handset two gimbal boxes show the stick channels: the Pocket's sticks as received when it is live (stale after 0.5 s, greyed), otherwise the channel defaults; the ground station sends no stick values. The channel assignment comes from the radio config's `[sticks]` table.
- **Dock tab marker** (the tab's alert state): amber while a Pocket loss is reported, red while the vehicle reports NOT MASTER or MULTI_MASTER.
- **Debug hook** `window.exgs.radio.debug()`: banner text and tone, button states, and per control the displayed position, enabled, lock state, padlock visibility and the µs text.

## Display settings (UI scale and 3D resolution)

Operations dock tab **Display** (`panels/display.js`, `display_settings.js`), stored per browser in `localStorage` key `exgs.display` (reads and writes wrapped in try/catch; an unusable store means Auto). Display only, nothing is sent to the vehicle.

The Display tab shows the resulting ratio. If the GUI looks very zoomed in on a small high-DPI screen (Steam Frame), lower UI scale to 75 % or 100 % and, if the 3D view is blocky, raise 3D resolution.

### Data rates (panel `rates`, always visible in the Bench Mission column, not a dock tab; `rates/rates_logic.js`)

User request 2026-11-20. The old per-source `pkt/s` (`LinkStats.rx_frames_s`) counts frames on the **serial hop** between the ground station and its USB peer. For the Router it is dominated by the Pocket's own RC_STATE copies (about 200/s), which never cross the air, so it says nothing about the radio speed. The panel shows the rate of each type of data with the path it took, from the core's `get_rates` (docs/api.md), polled once per second for the current data view (`ctx.rates()`).

- **Table** (sorted by path, then bytes/s): type, path, source (with the origin node), Hz over 2 s, Hz over 10 s, nominal Hz, bytes/s, age. Paths: **air** (frames from node 1 or 3 received through the Router), **usb direct** (the vehicle on its own USB), **router local** (made by the Router, node 2, and the Pocket's RC_STATE copy: never on the air), `simulated` (fake source, or a recording) and `unknown`. A **total row** closes each path. Nominal is the schema's `rate_air` on the air path and `rate_usb` elsewhere (a dash when the schema has none; for the fake source and replay the type's nominal rate). **Greyed**: not seen for 3 s (or three nominal periods), or a zero rate. **Orange**: below 70 % of the nominal rate (judged on the 10 s window below 2 Hz, so a 0.5 Hz stream does not flicker).
- **Bytes/s** are wire bytes as received on the serial line (COBS, delimiter, stream kind, CRC and network header included) when the profile reports the frame size (`exvectrnet-1` does); the air total and the bar use **payload** bytes. Packet-level streams (fake source, replay) have no byte counts and show `n/a`.
- **Air utilisation bars, one per direction** (the air link is time-division with a 1:1 split: 25 air packets/s of 253 payload bytes each way, about 6.1 kB/s of payload in each direction at the same time; the total is not shared): **Downlink** (ship radio node to Router to ground station, vehicle telemetry; measured: payload B/s of frames from node 1 or 3 received through the Router) against `[rates] air_capacity_down_bytes_s`, and **Uplink**, an **ESTIMATE** (labelled "estimated" on the bar and its tooltip) because the ground station cannot see uplink bytes: the GS `CMD_STATE` at the uplink rate of 25 Hz (14 B; the Pocket's `RC_STATE` no longer goes to the air) while the engine sends, `LINK_CONFIG` at its schema rate, plus the `REQUEST`s and telecommands this ground station sent through a Router, against `[rates] air_capacity_up_bytes_s` (both default 6100; `air_capacity_bytes_s` is a compatibility alias). Next to each bar the measured air packets per second against the 25 packets/s maximum, from the `air_rx_ok` counters of the Router (down) and the ship radio node (up); the downlink is limited by packets as well as bytes (each air packet carries at most 253 payload bytes and each packet type at most once). Amber above 80 %, red above 100 %. A measured uplink byte count would need a per-direction byte counter in the firmware's `LINK_STATS` (a possible later schema addition; not done). Below the bars the Router's own LINK_STATS (`RadioLinkStats`: air packets per second up and down, link quality). Details: docs/api.md `get_rates`.
- **Status bar**: the per-source chips are labelled "frames/s on the serial hop:" (tooltip: it is the ground station to Pocket/USB hop, not the radio rate) and an **air: X B/s** chip (payload bytes of the air path; `air: n/a` when not measured) follows them.
- **Replay**: the numbers are computed from the recording in replay time (the packets' own timestamps against the replay position, so pause, seek and speed behave), packet level only: no byte counts, so no air bytes (`air: n/a`); one wire frame can give several packet types, so Hz is per packet type. Paths come from the log's `#source` kind and the type (a log has no node ids).

- **Frames, not samples**: the table counts wire frames per packet type. An `AIR_ACTUATORS` frame (nominal 25 Hz, path air) carries **two** actuator samples, so the `Actuators` and `FlapState` panels, plots and recordings see an effective 50 Hz (the history keeps at most 20 Hz per series as for every type). `AIR_MISSION` is nominal 5 Hz. Nominal rates come from the schema (`rate_air`, `rate_usb`).

Tests: `web/test/rates_logic.test.js`, `tests/integration/test_rates_gui.py` (pty fake vehicles: table content and path labels; replay).

### Source on / off (link panel)

### Raw and calibrated sensor panel

`web/app/panels/rawsensors.js`, `web/app/sensors/rawsensors_logic.js` (`web/test/rawsensors_logic.test.js`). Panel `rawsensors`, "Raw and calibrated sensors". Consumes `ImuRaw` and `Calibration` (the vehicle's `CALIBRATION` packet, port 0x93, USB only, every 2 s). Needs the vehicle's USB debug set: with no connected `vehicle_usb` source in the live view the panel says so.

- **Raw (uncalibrated):** `ImuRaw` gyro (rad/s), accelerometer (m/s²), magnetometer (shown in µT, the packet is in T), pressure (Pa) and temperature (K), live, with the update age (stale values are struck through with their age, as everywhere), the magnitude of accel and mag, and a sparkline of the last 10 s (magnitude for vectors). The column header says **raw (uncalibrated)**.
- **Calibrated (computed here with the ship's formulas):** the formulas of flight-software `docs/project/hardware-and-drivers.md` section 8a, computed in the browser from the latest `ImuRaw` and `Calibration`, SI units: `gyro_cal = gyro_matrix * (gyro - gyro_offset)`, `accel_cal = accel_matrix * (accel - accel_offset)`, `mag_cal = mag_matrix * (mag - mag_offset)`, `omega_est = gyro_cal - gyro_bias_est`; matrices are row-major, `M[r][c] = matrix[3r + c]`. Calibrated values and magnitudes (|accel cal| should be about 9.81 m/s² when the vehicle is still) are shown next to the raw ones; the magnetometer in µT (the vehicle normalises |mag cal| to about 5 µT, which is not the physical field strength). A component that is NaN on the wire gives "n/a", never a guessed number; a `raw_frame` other than 0 (SENSOR) is not computed. **Display only:** nothing computed here is sent, stored, used for a decision or fed back anywhere.
- **Calibration state:** a line shows the age of the `CALIBRATION` packet (marked STALE when it is older than its limit, and the calibrated column is then dimmed) and the source flags per sensor, decoded: calib EEPROM, transform EEPROM, offset override (hard-coded), RAM only (not saved), memory cleared (defaults), or identity defaults when no bit is set. Until a `CALIBRATION` packet has been received the calibrated column shows `waiting for CALIBRATION packet` (and the state line `none received`).
- **Tests:** the formula is checked against the `imu_raw` and `calibration` cases of the Packets test vectors (`web/test/data/calibration_vectors.json` is a copy, a Python test fails when it drifts from `lib/ExVectrPackets/test/vectors/packets.json`).

`Estimator.att_std` changed meaning on the vehicle (packet version 2 here): it is the 1 sigma of small rotations about the **WORLD axes [North, West, Up]**, no longer a per-quaternion-axis value. The packet labels are `north, west, up` and the inspector shows them that way.

### Requests panel

Panel `requests` (`web/app/requests/requests_logic.js`, `requests_panel.js`; a dock tab, `inputs: true`: shown disabled with the lock line in the replay view). **Safety-relevant**: with the radio widget it is the only GUI path that makes the core send anything ([requests.md](requests.md)). Rules, enforced in the logic module and covered by `web/test/requests_logic.test.js` and `tests/integration/test_requests_widget.py`:

- **From the core's whitelist.** Rows come from `request.list` (group, label, target, confirm level, `route`); the GUI knows nothing about what an action means and has no other way to name an action.
- **Hold to send.** Each row's button needs a continuous hold of **1 s** (progress bar, same pattern as the radio padlock); a click, a short hold, a blur or a pointer leaving sends nothing. The panel never sends by itself.
- **`danger` actions** (`LINK_UPLOAD_MODE`, `LINK_REBOOT`) additionally open a modal after the hold, showing the row's own `warning` (for `LINK_REBOOT` on the ship radio node: a reboot in flight interrupts RC for seconds), else "This acts on a link module (the Router or the ship radio node): its radio link stops or restarts. The module always obeys, even in flight." Its send button is **disabled for 2 s** (countdown in the label); Cancel and Escape close it without sending; only the button sends `request.send` with `understand_link_stops: true`.
- **State from the core only:** each row shows the latest `requests` push for its (action, target): `sending, attempt n/5 via <source>`, `ACK <status as reported> (detail d)`, or `TIMEOUT`. `DONE` and `IN_PROGRESS` are green, any other status (and an unknown one) red, never an assumed success. The button is disabled while that request is in flight.
- **Disabled** in the replay view, without a connection, on a view-only host (`welcome.can_control` false), while in flight, and when no source can reach the target (`status.request_routes`); the core still refuses everything itself and its error text is shown under the list.

`ctx`: `options` (the layout entry's options), `store`, `schema`, `api` (`api.request(op, payload)` returns a promise of `data` or rejects with `{code, message}`), `fmt`, `h`, `Bindings`, `view()` (`"live"` or `"replay"`), `status()` (last `status` message), `rc()` (last `rc` push, `null` while disconnected), `now()` (view time), `switchView(v)` (asynchronous: view guards run first), `addViewGuard(async (nextView) => bool)` (returns a remover; a guard can veto a view switch, the radio uses it for the release prompt), `setTitle(text)`.

The object returned by `create` may have: `onPacket(pkt)` (per received packet of a consumed type in the current view; also called for the items of a snapshot), `onReset(view)` (snapshot replaced the store), `onTick(now)` (10 Hz), `onViewChange(view)`, `onStatus(status)`, `onEvent(evt)`, `onRc(rc)` (every `rc` push, `null` on disconnect), `onRequests(msg)` (every `requests` push), `onTelecommands(msg)` (every `telecommands` push, TEMPORARY), `onReady()` (after every connect), `freshness()` returning `{state, age}` for the header badge, `alert()` returning `""`, `"warn"` or `"bad"` for the dock tab marker, `destroy()`. Debug hooks of the shell: `window.exgs.layout` (`view()`, `set(id)`), `window.exgs.dock` (`open(tab)`, `mode()`, `tab()`), `window.exgs.source()` (data-source tag state).

Most panels only need `Bindings`:

```js
const b = new ctx.Bindings(ctx);
b.row(el, "Phase", { type: "MissionState", field: "mission_phase", kind: "enum" });
b.row(el, "Position", { type: "Position", field: "pos", kind: "vec", unit: "m" });

```

Value spec: `type` (or `types` for derived values), `field`, `index`, `src`, `unit`, `digits`, `scale`, `kind` (`num`, `vec`, `enum`, `bool`, `time`, `text`), `labels` (bool), `format(value)`, `derive(entry or entries)`. The cell options `tone(description)` (colour name) and `class` are the optional last argument of `row` and `cell`.

## Tuning view

View `tuning` (Alt+3): one graph workspace (panel `tuning`, `web/app/panels/tuning.js`) with the Operations dock in the rail. Screenshots `docs/img/tuning-1920.png`, `tuning-1366.png`.

- **Data.** On connect, view change, seek and window change the panel loads `get_history` with `buffer: "plot"` (docs/api.md): live the core's full-rate buffer (`PLOT_TYPES`, up to 200 Hz, the last 130 s, so a page reload keeps two minutes), in replay the open log (at most 600 s). Then every packet is appended from a subscription in mode `all` (every sample, not the 20 Hz latest-value stream). `Calibration` is taken from the store for the calibrated signals.
- **Signals** (`web/app/plot/catalogue.js`, unit tested): everything the vehicle sends (including GNSS altitude, relative GNSS altitude and the altitude difference, see "GNSS panel and altitude cross-check"): roll / pitch / yaw / tilt from q, body rates (`Attitude.omega`), position and velocity against `MissionState.sp_pos` / `sp_vel` and the errors target − current, horizontal speed, `Actuators` flaps / TVC / thrust / roll torque, `FlapState` angles (and commands if supplied), `TvcState`, `VehicleState.tvc_thrust`, gyro raw / calibrated / calibrated − bias estimate (`ImuRaw` + `Calibration`, the ship's formulas, display only), accelerometer and magnetometer raw / calibrated, |accel|, pressure, `Estimator` σ (attitude about N/W/U, velocity, position) and `TaskTiming` avg / max. Angles in degrees, rates deg/s, mag µT, timing ms; the unit is on every axis and legend entry. A signal that never arrived is shown as "not received" (grey in the picker), never as zero.
- **Ready-made graphs** (16, eight shown by default): attitude, angular rate, altitude vs target, position N/W vs target, velocity vs target, position error, TVC, thrust, flaps command vs angle, gyro x raw / calibrated / estimated, accelerometer and magnetometer raw vs calibrated, estimator σ attitude / velocity / position, task timing. One unit per graph (no second y axis); a target shares its value's colour and is dashed; at most eight series per graph in the validated categorical palette (`--s1..--s8`, dark and light).
- **Controls.** Window 10 s / 30 s / 2 min / all (remembered), Pause / Live (drag, the arrow keys or the wheel scroll and zoom while paused), + Add graph (presets or empty), Reset graphs, CSV of all graphs; per graph: Signals ▾ (grouped picker), auto y or manual min / max, CSV, PNG, remove. Graph sets are remembered in `localStorage` (`exgs.tuning.graphs`, sanitised on load).
- **Cursor.** Hovering any graph moves one shared time cursor across all graphs and the legends show the values at the cursor; without hover the legends show the latest values, and in replay the cursor is the replay position (scrubbing moves it, a seek reloads the window from the log, ending at the new position, so the graphs show the log's full history up to it with no gap). The x axis is seconds before now (live) or the log position (replay).
- **Performance.** Canvas, min/max decimation per pixel column (`web/app/plot/series.js`: 100 Hz over 2 min on 600 px is at most 1200 points per series), about 15 redraws per second only while the view is visible. Measured on the fake source (8 graphs, about 25 000 points drawn): about 1.5 ms per redraw. Browser test `test_browser_tuning_graphs_live_history_reload_and_replay` (live, reload keeps history, pause, replay).

**Missing telemetry for tuning** (to be requested from the flight software; nothing is invented here): attitude setpoint (quaternion or angles) and attitude error; angular-rate setpoint; controller terms per axis (P, I, D contributions, integrator states, output saturation flags); commanded vs achieved thrust and torque (it is not documented whether `Actuators` is command or feedback); flap commands (`FlapState.cmd` is not sent by the vehicle); acceleration setpoint; estimator innovations / residuals (GNSS, baro, magnetometer) and covariance diagonals beyond att/vel/pos σ (gyro and accel bias σ); estimated linear acceleration; barometric altitude; task names and valid `max` values for `TaskTiming` (all NaN on the bench), loop period and jitter; battery voltage and current; motor RPM / ESC feedback; the mission plan (list of upcoming points, time to the next phase).

## Command panel (replaces "RC applied")

Panel `command` (`web/app/panels/command.js`, logic in `web/app/command/command_logic.js`, `web/test/command_logic.test.js`), Operations dock tab "Command" next to Radio. **Display only**: it sends nothing, and its two halves are labelled apart so the sent state is never read as the applied one.

- **Sent by the ground station (command engine)**, from the `rc` push (`command`): the session (32 bit and low 16 bits), the input (Pocket / virtual panel / none), the Pocket stream state (not seen / live / LOST), the command stream and its links (`sending to usb, router (25 Hz)`, or `NO COMMAND LINK CONNECTED`), the sent state (`go`, profile, REAL / SIMULATION, motors armed / disarmed, SE, failsafe), `NOT MASTER` and `MULTI_MASTER` when the vehicle reports them, and the pickup hints.
- **Applied by the vehicle** (`CMD_APPLIED`, port 0x84, USB only, so it has data only on a direct USB connection to the vehicle): the last accepted `go`, profile, vehicle mode (the field, not the applied mode), motors armed / disarmed, SE, failsafe request, the information flags (`POCKET_LIVE`, `INPUT_VIRTUAL`), the latched session, the four safe-value-seen bits (GO, SC real, SD armed, SE press), the age of the last accepted `CMD_STATE` (either link, USB, UART) and the four wrapping reject counters (bad length or field, source not node 0, foreign session, stale or duplicate). Used to compare every Pocket and virtual switch with what the vehicle decoded.

The status bar cell **Command source** (key `ctrl_source`, replaces "Control source") shows the vehicle's `ctrl_source` (GS or NONE), the latched session (low 16 bits of `VEHICLE_STATUS.cmd_session`, hex), `NOT MASTER` (red) when that session is not this core's, `MULTI_MASTER` and `GS_FAILSAFE_REQ` (red), and which links are fresh (`USB fresh`, `UART fresh`, `USB+UART fresh`, amber `no link fresh`). `NOT MASTER` is display only: the engine keeps sending and the vehicle decides.
